community detection · post-proc · connected-component split

CC

connected components · Park 2025 / Vu-Le 2026

Cheapest of the three connectivity post-procs. One breadth-first sweep per cluster; every connected piece becomes its own output cluster. No threshold, no parameters: a sanity pass that catches partitions whose clusters are not actually connected.

Some clustering algorithms emit a label per node without checking that the nodes carrying that label are reachable from each other. Stochastic block models are the most frequent source: they fit edge density between blocks, not whether each block is internally connected. A cluster can end up as two disconnected halves under the same label, and the output looks like one community when it is really two.

CC is the correction. For each cluster in the input partition, drop every edge that crosses out to a different cluster, run a breadth-first search on what remains, and replace the cluster with one new cluster per connected piece. If the cluster was already connected, nothing changes.

The cost is one breadth-first search per cluster, \(O(|V| + |E|)\) over the whole graph. In plain terms: every node and every intra-cluster edge gets touched once, no more. Two interesting properties: cost is independent of the number of input clusters (the search sweeps the residual graph in one pass over the whole node set); and there is no parameter to tune, no threshold to set, no model to fit.

cross-cluster edge an edge whose endpoints carry different input cluster labels. CC drops every such edge before the breadth-first search.
residual graph the subgraph that survives after the cross-cluster edges are dropped. Same node set as the input; only intra-cluster edges remain.
singleton component a connected component of size one in the residual. CC drops these from the output; nodes that fall into a singleton end up unlabelled.
why this matters · Park 2025 / Vu-Le 2026

On graph-tool's flat and nested stochastic block models (every variant tested: degree-corrected, non-degree-corrected, planted-partition, plus PySBM), internally disconnected clusters show up across both real and synthetic benchmarks. Splitting them with CC improves accuracy on most of those benchmarks. WCC adds a connectedness threshold on top and gains more; CM adds a re-clustering pass on top of that and gains the most. CC is the cheapest correction of the three.

The page below walks one full CC pass on the shared 32-node fixture, stage by stage. Each stage owns its own viz frame; the centerpiece in the middle is the frame-by-frame walker over every read and write the algorithm performs.

stage 1 · why post-process

What a base clustering can leave behind.

Base community-detection algorithms maximise a quality function on the partition: modularity for Louvain and Leiden-Mod, CPM for Leiden-CPM, description length for Infomap, log-likelihood for SBM. None of those quality functions directly penalise a cluster that ends up internally disconnected; under modularity, for instance, two disjoint pieces under one label contribute the sum of their internal-edge counts and pay one configuration-model penalty for the combined degree mass, which can score better than two separate labels paying two penalties. The algorithm has no reason to keep the pieces apart.

The viz below highlights cluster C on the fixture: nodes 20-25 share one label even though the two 3-cycles are not connected to each other within the cluster. A base algorithm that emits this partition is not broken; it is optimising what it was told to optimise. CC is the second pass that turns each label-with-multiple-pieces into one label per piece.

spotlight on cluster C · two disjoint 3-cycles sharing one label colour = input cluster id

The same situation can happen on any base. Stochastic block models are the most frequent source because they fit on between-block edge density; planted-partition variants in particular can place two dense sub-blocks under one block label when no inter-block edge runs between them. Leiden's refinement phase reduces the chance but does not eliminate it on graphs where merge candidates straddle a label boundary. CC catches every case regardless of which base produced it.

stage 2 · the rule

One inequality, two regions.

CC's test, written explicitly:

\[ |\{\text{connected components of } G[C]\}| \;\ge\; 1 \]

where \(G[C]\) is the subgraph of \(G\) induced by the cluster's node set, restricted to intra-cluster edges. In plain terms: if the cluster's residual induced subgraph breaks into more than one connected piece, CC emits one output cluster per piece; if it stays as one piece, the cluster passes unchanged. The inequality is loose at one (the trivial case where the cluster is connected) and tight when the cluster has been split.

Two interesting properties of this rule. It says nothing about the strength of the connection: a cluster joined by a single bridge edge is still one connected piece, so CC passes it through. The harder test that catches the bridge case is the WCC threshold, which compares the cluster's minimum cut against a size-dependent bound. And the test is local to the cluster: the verdict on cluster \(C\) depends only on the edges between \(C\)'s own nodes, not on what the rest of the graph looks like, so the same cluster has the same verdict regardless of the partition's other contents.

where CC stops and WCC begins

CC's rule is binary connectedness: split iff the residual subgraph has more than one component. WCC replaces this with a strict inequality on minimum edge cut: \(\text{mincut}(C) > f(|C|)\). The two coincide when \(f(n) = 0\): the threshold-zero mode collapses the recursive cut and threshold loop to CC's single breadth-first-search sweep. CC ships as the same binary that hosts WCC and CM, invoked with the threshold disabled; the technical companion below pins the file and the flag.

stage 3 · drop cross-cluster edges

Build the residual graph.

The first concrete step is to walk every edge in the input and decide whether to keep it. An edge \((u, v)\) survives iff \(u\) and \(v\) carry the same input cluster id. Edges crossing between clusters get dropped. The node set does not change; only the edge set shrinks.

The viz below paints every cross-cluster edge red and every intra-cluster edge in its cluster's colour. On the fixture, six edges cross between clusters and 46 stay. CC's residual graph is the same 32 nodes with those 46 edges; the breadth-first search runs on that residual.

residual graph · red = cross-cluster (dropped) · coloured = intra-cluster (kept) ·

Worth noting: the residual graph is not necessarily connected even at the whole-graph level. The two 3-cycles in cluster C are joined to the rest of the graph only through edges \((20, 7)\) and \((23, 13)\), both of which cross into other clusters and get dropped. After the cut, the two 3-cycles sit as isolated 3-node islands. The outliers 30 and 31 lose their pendant edges to cluster A for the same reason; they end up as a 2-node island whose own edge \((30, 31)\) is intra-outlier and survives, but the outlier label means CC will drop the resulting component at the singleton filter.

stage 4 · cluster scan

For each input cluster, count the residual components.

With the residual graph in hand, CC walks the input clusters in id order and runs a breadth-first search on each cluster's induced subgraph. The quantity recorded per cluster is the number of connected components in the residual.

stage 6 · cluster A walkthrough

A connected cluster passes through unchanged.

Cluster A holds 12 nodes. Of its 17 intra-cluster edges, 10 sit inside the \(K_5\) core on \(\{0,1,2,3,4\}\) and 7 attach the periphery nodes 5-11 to the core. The breadth-first search starts at node 0 (the lowest unvisited node in the cluster), enqueues its neighbours in the core, then their periphery attachments. Every node is reached in a single sweep. The kernel records one component of size 12, which becomes one output cluster after the singleton filter.

cluster A residual · 1 component · 12 nodes BFS root = node 0

Two properties of the BFS on a connected cluster. The visit order is determined purely by the residual adjacency, which is in turn determined by edge insertion order in the input edgelist. CC reads the edgelist in CSV row order; the kernel sorts each node's adjacency in ascending neighbour-id order to match the canonical binary's igraph layer, so the per-frame trace is reproducible across runs. And no node ends up unvisited: every periphery node has at least one edge into the core, so the single sweep from node 0 reaches the whole cluster.

stage 7 · cluster B walkthrough

The bridge case: connected but barely.

Cluster B is two \(K_4\)s joined by the bridge edge \((15, 16)\). The breadth-first search opens at node 12, enqueues its neighbours \(\{13, 14, 15\}\) inside the first \(K_4\), then reaches node 16 via the bridge once node 15 is popped, then enqueues 16's neighbours \(\{17, 18, 19\}\) inside the second \(K_4\). Every node is reached; one component of size 8 is recorded.

cluster B residual · 1 component · 8 nodes (via the (15,16) bridge) BFS root = node 12

CC passes B through even though the bridge is a single edge whose removal would split the cluster cleanly into two \(K_4\)s. CC's verdict only counts connected components; a 1-edge cut is still one component. The case where 1-edge connectedness should fail is the bridge case that WCC catches with its threshold on minimum cut. On this fixture, WCC under \(\log_{10}(n)\) at \(n=8\) lands at threshold \(\approx 0.903\), and the cut of 1 strictly exceeds it, so even WCC keeps B together; the doubled coefficient \(2 \log_{10}(n)\) at \(n=8\) lands at \(\approx 1.806\), which 1 fails. The point is that CC has no knob to turn for this case; CC and WCC differ on whether one cares.

stage 8 · cluster C walkthrough

The split case: two pieces under one label.

Cluster C is the diagnostic case. Six nodes \(\{20, 21, 22, 23, 24, 25\}\) all carry the same input label, but the residual subgraph holds only the two 3-cycles. The breadth-first search opens at node 20, sweeps its 3-cycle \(\{20, 21, 22\}\), finds no further unvisited neighbours, and terminates with one component of size 3. The outer loop then walks forward in node id order, finds node 23 unvisited, opens a second breadth-first search there, sweeps the second 3-cycle \(\{23, 24, 25\}\), and terminates with a second component of size 3.

cluster C residual · 2 components · sizes (3, 3) BFS roots = 20, then 23

C is the only cluster on the fixture whose verdict changes. The two components inherit fresh component ids during the breadth-first search itself: \(C_1 = \{20, 21, 22\}\) gets id 2 (the third component discovered overall, after A and B), and \(C_2 = \{23, 24, 25\}\) gets id 3. Both have size greater than one, so both survive the singleton filter and become two distinct output clusters. The original cluster label is not preserved: the surviving pieces get fresh output ids assigned in the order they were discovered.

stage 9 · cluster D walkthrough

A path-shaped cluster passes through.

Cluster D is a 4-node path: edges \((26, 27)\), \((27, 28)\), \((28, 29)\). The breadth-first search opens at node 26, walks down the path one hop at a time, reaches every node, and terminates with one component of size 4. The bridge edge \((27, 28)\) is the cluster's whole connectivity; removing it would split D into two 2-cliques. The connected-component count is one regardless, so CC passes D through.

cluster D residual · 1 component · 4 nodes along a path BFS root = node 26

The pattern across A, B, C, D is the property worth keeping. CC's verdict per cluster depends only on how many connected pieces the residual subgraph holds. The cut value, the bridge count, the cluster density: none of those feed the test. A, B, D pass with one component each, and C splits into two; the whole algorithm reduces to that count.

stage 10 · singleton filter and id assignment

Drop size-one components, number what remains.

After the per-cluster breadth-first search, the kernel walks every node in id order and buckets it into its component. Buckets of size one are dropped; nodes in those buckets end up unlabelled in the output. On the fixture this drops nothing from the labelled clusters (every surviving component has size at least three) but does drop the singleton outliers if the input partition placed them in size-1 labels. The pendant pair \(\{30, 31\}\) shares the outlier id, so they form a size-2 component and survive as a separate output cluster.

The surviving components are then emitted in discovery order. The output cluster id for each component is assigned by a first-in-first-out queue: the first component popped gets id 0, the second gets id 1, and so on. Cluster ids are dense \([0, K)\) with \(K\) the number of surviving components. The original input cluster id is not preserved.

after filter + id assignment · coloured = output cluster id ·

Two properties of the assignment. The output id is determined by component-discovery order, which is determined by the per-cluster breadth-first search order, which is determined by input node id ascending. So the same input edgelist and the same partition always produce the same output ids on every run: CC is deterministic. And the assignment is dense, so downstream tools that index by cluster id (a per-cluster array, for instance) do not need to handle gaps.

stage 12 · why split-only

What CC does not do.

CC's role is narrower than "fix the clustering". The remit covers one structural fault and nothing else; listing what falls outside it clarifies the picture.

no re-clustering CC never re-runs the base community-detection algorithm on the split halves. After a split, both halves are emitted as-is. CM is the sibling that re-runs Leiden (or whichever base) on each half; that is the headline difference between the two.
no merging the post-proc only splits; it never combines two input clusters into one. If the input partition under-splits a community (one ground-truth community labelled as two clusters), CC cannot fix it.
no label preservation the original input cluster id is not carried into the output. Surviving pieces get fresh ids assigned in breadth-first-discovery order. Code that needs to track the lineage from input cluster id to output cluster id has to maintain the mapping externally.
no cut work the breadth-first search counts components; it does not measure or use minimum-cut values. The bridge case (one connected piece joined by a single edge) passes through unchanged. The cut-based test is WCC's.
no parameter there is no threshold, no resolution, no minimum cluster size. The output partition on a given input is uniquely determined.

Two properties of "split-only". The output partition is a refinement of the input partition restricted to the labelled nodes: every output cluster's node set is a subset of some input cluster's node set. So no inter-cluster edge in the output exists between two pieces of one input cluster: the cross-cluster edges that the residual cut dropped are exactly the edges that would lie inside such a pair in the output. And the count of output clusters is at least the count of input clusters (modulo singleton drops): CC can leave the count unchanged or grow it, never shrink it.

stage 13 · chain composition

Where CC sits in the pipeline.

CC is the first of three connectivity post-procs that sit downstream of a base community-detection algorithm. The chain is base, then CC, then optionally WCC, then optionally CM. Each stage adds work: CC catches disconnected clusters; WCC also catches bridge-only clusters; CM re-clusters the cut halves through the base algorithm.

base Leiden-Mod · Leiden-CPM(0.5) · Infomap · SBM-Flat-PP
→
post 1 · here CC · split disconnected clusters
→
post 2 WCC · recurse on mincut threshold
→
post 3 CM · re-cluster each cut half

The bumped three-tier verification panel grids 161 networks (small / medium / large), 50 random seeds, four base partitioners, and the chain of post-procs above. Each chain produces a partition on every cell; the kernel on this page is checked against the binary at the CC output. The cumulative match count across the chained CC sweep is 0 mismatches over the 8050 cells of each base.

Two interesting properties of the chain. Each post-proc only ever shrinks node-membership-per-cluster relative to its input: CC, WCC, and CM all emit refinements of their input partition, never coarsenings. So the chain is monotone in cluster count (modulo dropped singletons) and the final partition cannot have a cluster that is a superset of any intermediate cluster. And the chain is stateful only in the partition it carries: each stage takes a partition in and emits a partition out, so the chain can be paused, branched, or recomposed without re-running the base algorithm.

stage 14 · failure mode

Where CC over-splits a planted community.

CC's failure mode is the small planted cluster with low internal connectivity. If a planted community is two dense pieces with no edge between them, CC splits correctly; the base algorithm under-merged and CC fixes it. But if the planted community is genuinely sparse, with two near-isolated pieces that happen to share a label because the analyst designed it that way, CC still splits and the output disagrees with the planted partition by exactly that split.

Reading this as a failure or a fix depends on what the analyst wants. CC's invariant is structural: the output partition has no internally-disconnected cluster. The planted partition may carry semantic content that the topology cannot see (two pieces are "one community" because they share an attribute, a label, an origin). CC has no access to that semantic content; the post-proc only reads edges.

A cluster with no internal edges.
Every cross-cluster edge gets dropped, so the cluster's residual subgraph has no edges left. Each node sits on its own. The breadth-first search reaches nothing past its starting node. Every node becomes a singleton, the singleton filter drops them all, and the cluster vanishes from the output. The pre-CC count of nodes in this cluster goes to zero in the post-CC count.
A single-node cluster.
One root, one component of size one, dropped at the filter. CC treats outliers and singletons identically: gone from the output. The fixture's nodes 30 and 31 share the singleton outlier label and form one size-2 piece via their pendant edge, so they survive as one output cluster; the failure mode here is the opposite of what the planted partition expected.
Planted community with a 1-cut bridge.
The bridge keeps the cluster as one connected piece, so CC passes it through unchanged. The size-dependent threshold in WCC is what catches the bridge case explicitly. CC has no setting that distinguishes it from a denser join.

Vu-Le 2026 reports CC's gain over the unprocessed clustering across both flat and nested stochastic block models. The aggregate gain holds, but on inputs whose planted communities include genuinely sparse or genuinely disconnected pieces (rare in the benchmark suite, more common in domain-specific real networks), CC splits a cluster that the ground truth keeps together. CM's re-clustering pass can recombine a merged label after such a split, so the chain behaves differently from CC alone on this class of input.
