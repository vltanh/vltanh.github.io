CM

connectivity modifier · Park 2024

The heaviest of the three connectivity post-procs. WCC's cut, plus a re-run of the base community-detection algorithm on each cut half before the recursion advances. Iterates to a fixed point where every output cluster is both well-connected and locally optimal under the base objective.

Three sibling post-procs sit between a clustering algorithm and the final output. CC drops every cross-cluster edge and replaces each cluster with its connected pieces, a structural sanity pass that catches partitions whose clusters are not even connected. WCC adds a threshold: a cluster has to clear a sliding mincut bound or it gets cut and recursed. CM is the heaviest of the three. It does what WCC does, then runs the base community-detection algorithm again on each cut half before the recursion continues.

The word in "connectivity modifier" carries weight. CC and WCC are filters: they keep what passes and split what does not, but the output labels are descendants of the input labels. CM modifies: the post-cut halves are not stuck with the input partition's idea of who-belongs-where. If the base algorithm sees an 80-node induced subgraph and decides it is really four communities, CM accepts that and feeds the four communities back into the next round. The output cluster set is a function of the base algorithm plus the threshold, not just the input partition.

Reading the steps another way: CM is a fixed-point iteration. Starting from the input partition, repeat {check connectivity threshold; on failure, cut + re-cluster; on success, accept the cluster as a survivor}. The iteration terminates when every remaining cluster is a fixed point of both the threshold check (its mincut exceeds the bar) and the base algorithm's local view (the base algorithm on the cluster's induced subgraph returns the cluster itself, not a different partition). The output is a partition where both properties hold cluster by cluster.

The threshold uses the same parser as WCC:

\( f(n) = C \log_x(n) \quad \text{or} \quad f(n) = C\,n^x \)

In plain English: a cluster of \(n\) nodes passes iff its minimum edge cut is strictly larger than \(f(n)\). The threshold grows with cluster size, so small clusters can clear a low bar but large ones have to be more internally robust. Two interesting properties: the threshold is monotone in \(n\), so as a cluster shrinks under repeated cuts, the bar it has to clear shrinks too, which is why the recursion terminates; and the threshold is independent of how dense the cluster is overall, only of its size, so a sparse 20-node cluster and a dense 20-node cluster face the same bar.

Park 2024 (PLOS Complex Systems 1(3):e0000009) gives \( f(n) = \log_{10}(n) \) as the paper's primary criterion. The pipeline wrapper ships \(0.2 \cdot n^{0.5}\) instead, a sqrt criterion that diverges from the paper's default. The two cross at \(n = 100\); below that, the log criterion is stricter.

The threshold shape is one of the most-discussed choices in the paper. Four candidates appear in Park 2024's analysis. \(\log_{10}(n)\) is the slowest-growing and most lenient: even at \(n = 2000\), the bar is around 3.3 edges, which most non-trivial clusters clear. \(\log_2(n)\) is roughly 3.3 times faster-growing and corresponds to a stricter version. \(\sqrt{n}/5\) is somewhere between the two for moderate \(n\), and dominates the log functions for \(n > 1000\). \(0.01 \cdot (n - 1)\) is the Traag-CPM lower bound: extremely strict, treating clusters as Potts-model-faithful only when their connectivity is linear in size. The paper picks \(\log_{10}\) as the primary default on the empirical observation that it catches the worst pathologies without forcing every cluster to be densely connected throughout.

pipeline shape Park 2024 splits the procedure into four stages: (1) initial base clustering produces the input partition; (2) a size filter drops clusters below \(B\) (default 11) plus tree-shaped clusters; (3) the CM loop runs per cluster, with each round doing mincut, threshold check, and base-method recluster of any side larger than one node; (4) a final size filter drops sub-clusters that ended up below \(B\). The walker below covers stage 3. Stages 2 and 4 live in the Python orchestration around the binary, not in the binary itself.
re-cluster step CM does not re-run the base algorithm globally. It runs the base algorithm on the induced subgraph of one cut half, then again on the other half. Each call gets a fresh seed; only VieCut's mincut RNG state drifts across rounds within a single binary run.
cluster fate Park 2024 §4.2 classifies every input cluster as one of four fates: extant (unchanged), reduced (smaller but still one cluster), split (two or more sub-clusters), degraded (every leaf descendant ended up below the size filter \(B\)). The binary writes a tree of parent → children so each input cluster's fate is reconstructable downstream.
pre-prune Park 2024's Stage 3 specifies an iterative pre-prune that strips low-degree nodes (degree below \(f(n)\) in the cluster's induced subgraph) before the cut. The binary exposes a partial version via the prune flag; the wrapper does not pass it. Today's CM runs without pre-prune by default; the full degree-band prune lives in the Python wrapper.
why "modifier" and not "filter"

CC and WCC are filters in the strict sense: every output cluster is a subset of nodes that all carried the same input label. CM does not keep that property. When CM splits a 50-node cluster and asks the base algorithm to re-cluster each side, the two sides can produce communities whose membership is whatever the base algorithm decides. The CM output partition's individual clusters are still subsets of input clusters (CM never crosses cluster boundaries in stage 3), but the per-cluster labels are not inherited from the input, they are minted by the base algorithm in the inner loop. That is the "modify" part.

why Leiden as inner re-clusterer, not Louvain

The base algorithm choice matters in the re-cluster step. Leiden's refinement phase guarantees every output community is internally connected, which means the subsequent connectivity sweep on the re-cluster output usually splits nothing further. Louvain has no such guarantee, so the connected-components sweep after Louvain's re-cluster can fragment communities further and pad the work queue. Both are supported in the binary; the deployed CM pipeline defaults to Leiden-CPM. Infomap is in the binary too but the wrapper does not accept it.

when CM moves the needle · Park 2024 §4.4

Heaviest gain comes on Leiden-CPM at small resolution (\( r \in [0.0001, 0.001] \)) where the base algorithm over-merges; CM peels apart real sub-communities that CPM left bundled. Lightest gain (or even slight loss) on already-conservative algorithms like IKC at k=10, where most clusters come through unchanged. Leiden-Mod sits in between, with a meaningful fraction of its clusters split. The paper's empirical reading: CM acts as a sharpener for over-merging base algorithms; less so as a corrector for over-splitting ones.

edge weights and termination

The binary builds VieCut's input graph with edge weight 1 on every edge regardless of any weight attribute on the input. Mincut therefore counts edges, not weights. Termination of the CM loop is not a formal theorem: each round either shrinks the largest pending cluster (via a cut) or replaces it with multiple smaller communities (via re-cluster), but a base algorithm that returns the same single community on a side that just failed the threshold can in principle cycle. In practice Leiden CPM at low resolution converges, and a sufficiently small residual eventually clears the threshold once \(n\) drops below the relevant cross-over point.

What CM does NOT do, as a class of corrections. CM only modifies clusters by splitting them; it never merges two input clusters into one. So if the base algorithm over-splits (produces two clusters where one was the right answer), CM has no mechanism to combine them. CM is a one-way operator: input cluster → subset of input cluster, or input cluster → multiple subsets, never input clusters → merged superset. The post-proc family's other operations (CC, WCC) are similarly one-way. The merging side is the domain of the base community-detection algorithm itself; CM trusts the base algorithm on merge decisions and re-examines only the split decisions.

Where CM differs from a hypothetical alternative

A few alternative designs to CM would catch different things. Listing them clarifies what CM is and is not.

An iterative-refinement alternative. Instead of CM's "mincut, then base-algo recluster", a refinement-style post-proc could iteratively move nodes one at a time, accepting moves that improve internal connectivity. This is closer to what Leiden's refinement phase already does inside the base algorithm; running it as a post-proc would amount to re-running Leiden's refinement on each input cluster's induced subgraph. The cost would be similar to CM's; the catch set would be similar too, because Leiden's refinement is the dominant force shaping CM's re-cluster output. CM is a less compute-heavy alternative that uses mincut as a faster diagnostic.

A modularity-or-CPM-recheck alternative. Re-evaluate the base algorithm's quality function on each cluster's induced subgraph; if the cluster is not a local optimum of the quality function on its own subgraph (e.g. removing one node would increase the score), modify the cluster. This catches different pathologies than CM: a cluster can have a fine mincut and still be sub-optimal under modularity (e.g. one peripheral node fits better as a singleton). CM does not catch this case. The trade-off: modularity-recheck is base-algorithm-specific (a different base means a different recheck), CM is base-algorithm-agnostic.

A global re-run alternative. Instead of re-clustering each cut half, run the base algorithm again on the whole graph after every cut. This is more expensive (one global re-run per cut) and less informative (the global run mostly returns the same partition because the global structure has not changed). CM's local re-cluster on the cut half only is a deliberate scoping choice.

None of these alternatives is universally better. They differ in cost, in catch set, and in what they trust about the base algorithm. CM's design splits the labour: trust the base algorithm on merge decisions, re-examine split decisions via a connectivity-only diagnostic, fix split decisions via a local re-run of the base algorithm. The three steps are independent in the sense that changing any one of them gives a different post-proc, but together they form the algorithm Park 2024 specifies.

A digression on edge weights

The binary builds VieCut's input graph with edge weight 1 on every edge, regardless of any weight attribute on the input edgelist. Mincut therefore counts edges, not weights. This is a design choice with consequences: a cluster joined by one high-weight edge (intuitively, a strong link) has the same mincut as a cluster joined by one low-weight edge, because both are mincut = 1 under the unweighted interpretation.

For unweighted graphs this is the right choice. For weighted graphs it is a simplification. Park 2024 frames CM as operating on a binary connectivity model: an edge exists or does not. The threshold function takes cluster size as input, not cluster weight, so the binary model is internally consistent. Users wanting weighted CM behaviour can pre-process the input by replacing weighted edges with multi-edges (a weight-2 edge becomes two edges in parallel), which makes mincut count weights. The wrapper does not do this; it leaves the input as-is.

The Leiden base algorithm reads edge weights when they are present (CPM and Modularity both use weighted formulations), so the re-cluster step is sensitive to weights even though the mincut step is not. This is one of the small inconsistencies of the CM design that the gallery surfaces. On the 32-node fixture every edge is unweighted, so the issue does not arise; on weighted inputs, the threshold check and the re-cluster step disagree on what "edge importance" means.

stage 1 · the threshold and the seed step

What the threshold says and how the work queue gets seeded.

CM's first action is the same as WCC's: drop every cross-cluster edge, take connected components of the residual, push each non-trivial component onto the work queue. The seed step splits cluster C (its two disjoint 3-cycles share one label) into two components before the mincut loop sees them. The other planted clusters arrive at the queue as single components.

The seed step adds one wrinkle CC and WCC do not have: lineage id assignment. CM tracks which output cluster descended from which input cluster, because the cluster-fate classification depends on the tree of parent → child relationships. The rule:

\( \text{if } |\text{component}| = |\text{original cluster}| \text{ then keep the original id, else mint a fresh id and record (parent } = \text{original, child} = \text{fresh)} \)

In plain English: if a component covers its entire input cluster, CM keeps the original cluster id (no fragmentation, no fresh allocation). If the component is a strict subset, CM mints a fresh id and adds a row to the lineage tree saying "this fresh id has the original id as its parent". The first fragment of each input cluster also adds a row "(parent = root, child = original id)" exactly once. Two interesting properties: the root row records every input cluster that ever fragmented, so the cluster-fate analyzer can find the split inputs by scanning a single row; and the lineage tree never re-uses an id, so the tree is always acyclic with depth equal to the number of cut rounds a cluster survived.

The "first fragment" rule deserves a closer look. When an input cluster fragments into two or more components, all of them are strict subsets, so all of them get fresh ids. But the row "(parent = root, child = original id)" is added exactly once, on the first encounter of the original id during the seed-step iteration. Subsequent encounters of the same original id during the same fragmentation skip the root-row insertion (the linear-scan dedupe at the binary level). The result: the root row's length equals the number of distinct fragmented input clusters, regardless of how many fragments each produced. This is what makes the root row a compact index of "every input cluster CM touched at the seed step".

One subtlety in the seed step iteration order: components are visited in component-id ASC order, which corresponds to the order BFS discovered them (the BFS starts from node-id 0 and walks the residual graph). Within each component, the first node is the lowest-id node in the component. The "(component is the entire input cluster)" check compares sizes, not node sets, so two different fragmentations that happen to produce the same number of nodes would both pass the check (and skip fresh-id allocation). In practice this case requires a coincidence: an input cluster whose first BFS-visited component happens to equal its full size. For most clusters this is impossible (the full size is the cluster's size, which by definition matches one component when the cluster is internally connected).

Why the seed step uses BFS instead of, say, depth-first search or some union-find-based component algorithm: BFS produces components in a stable order across runs (the BFS root is the lowest unvisited node id), and the components themselves are produced in node-id sorted order within each component. Both properties matter for byte-equal verification. A union-find based component algorithm would produce the same set of components but in a different iteration order; a DFS would produce the same components but with different within-component ordering. The BFS choice locks both orders in, so the byte-equal verification's per-component traversal order matches across the JS port and the canonical binary.

The threshold itself sits at the same place WCC reads it: \( f(n) = \text{pre\_log} \cdot \log(n) \), where \( \text{pre\_log} = C / \log(x) \) is precomputed once at startup. Per cluster the cost is one log of the cluster size plus one multiply by the precomputed constant. For the default \(1 \cdot \log_{10}(n)\), evaluate \(\log_{10}(12) \approx 1.079\), \(\log_{10}(8) \approx 0.903\), \(\log_{10}(4) \approx 0.602\), \(\log_{10}(3) \approx 0.477\). The strict comparison is \( \text{cut} > f(n) \), with a 1e-9 epsilon guard that treats borderline cases as fail.

Reading the formula another way: the threshold function decomposes into a constant (\(\text{pre\_log}\), set once at startup) and a per-cluster log evaluation. The constant captures the user's choice of \(C\) and \(x\) in \(C \log_x(n)\). The log evaluation is a natural log of the cluster size, scaled by the constant to give the user's intended logarithm. The trick is mathematical: \(C \log_x(n) = C \cdot \log(n) / \log(x) = (C / \log(x)) \cdot \log(n) = \text{pre\_log} \cdot \log(n)\). One log call per cluster, one multiply, done. The precomputation saves a per-cluster division.

Cluster A (12 nodes, 4 periphery pendants attached by single edges) has minimum cut 1, threshold 1.079: 1 is not strictly greater than 1.079, so A fails the first check. Cluster B (8 nodes, two K4's joined by one bridge edge) has mincut 1 and threshold 0.903: 1 > 0.903, so B passes. Clusters C1, C2 (3-cycles, 2-edge-connected), and D (4 nodes, mincut 1) all pass at their respective thresholds. Only A enters the second round.

What "well-connected" means as a constraint

Stripped to its core, the threshold check asks: after cutting the cluster's weakest link, do the two halves still hang together by more than a logarithmic factor of edges? A cluster of \(n\) nodes with \(\log_{10}(n)\) as the bar needs at least \(\lceil \log_{10}(n) + \varepsilon \rceil\) edges between any two halves. For \(n=12\), that is at least 2 edges. For \(n=100\), at least 3. For \(n=10000\), at least 5. The bound is mild on purpose; Park 2024 sets it that way to catch the worst pathologies (tree-like clusters with mincut 1, dumbbell clusters with a thin bridge) without forcing every cluster to be densely connected throughout.

Compare against alternatives. A constant threshold (cut > 1 always) catches only mincut-1 cases and lets everything else through. A linear threshold (cut > \(0.01 \cdot n\)) corresponds to a Traag CPM lower bound at \(r = 0.01\) and is sharply more aggressive for \(n > 1000\). The log threshold sits in between, asymptotically lenient but strict enough on small and medium clusters to flag the obvious thin-bridge cases.

why the strict greater than and not greater than or equal

The comparison at the threshold equality boundary is asymmetric on purpose. A cluster sitting exactly at its threshold (cut = \( f(n) \) to within 1e-9) gets treated as not well-connected and re-enters the queue. The next round's mincut may produce the same threshold, but by then the cluster is smaller, the threshold has shrunk, and the strict comparison favours the cluster again. The asymmetry biases toward more cuts, which is the safer call for a connectivity post-proc whose job is to find under-cohesive clusters; the cost is that a barely-passing cluster gets a needless extra split. Park 2024 picks this side of the boundary on the same logic.

the 1e-9 epsilon: why and when it matters

The threshold is a double-precision float; the cut is an integer. Equality in floating point is fragile. For criterion \(1 \cdot \log_{10}(100) = 2.0\), the computed double is not exactly 2.0 because \(\log(100) / \log(10)\) accumulates rounding. The 1e-9 tolerance treats anything within a billionth of the integer as a tie, and the strict comparison sends ties to the "fail" side. For criterion functions that hit integer values cleanly (like the piecewise variant), the tolerance is a no-op. For log and sqrt criteria, it catches the boundary cases at the integer-power-of-base sizes (\(n = 10, 100, 1000\) under \(\log_{10}\)).

stage 1b · reading the threshold check

The well-connectedness test, line by line.

The threshold check is a four-line routine, but every line carries a decision worth a sentence. Reading it forward: compute the threshold value as a product of a precomputed constant and a log of the cluster size; check whether the threshold and the cut differ by less than a billionth (the \(\varepsilon\) guard); then check whether the threshold is strictly less than the cut, with the tolerance check overriding equality.

\( \text{threshold} = \text{pre\_log} \cdot \log(n) \)
\( \text{is\_close} = | \text{threshold} - \text{cut} | \leq 10^{-9} \)
\( \text{well\_connected} = (\text{not is\_close}) \wedge (\text{threshold} < \text{cut}) \)

In plain English: a cluster is well-connected if its cut is strictly above the threshold AND the cut is not numerically tied with the threshold. The "not is_close" guard handles the floating-point equality case; the strict inequality handles everything else. Two interesting properties: the order of operations matters here, because pre_log * log(n) is one FMA-fusable site in C++ and the binary compiles with -ffp-contract=off to keep the computation byte-equal between machines; and a smaller cluster always has a smaller threshold (since log is monotone increasing for \(n \geq 1\)), so a cluster that fails the threshold once cannot recover by surviving a cut that just shrunk it further. The threshold-vs-cut relationship is monotone in cluster size.

The cluster-side cost per check is fixed: one log primitive, one multiply, one absolute value, one subtraction, one comparison, one AND. Compared to the cactus mincut on the same cluster (which is near-linear in cluster edges), the threshold check is negligible. The CM cost per round is dominated by the mincut plus the re-cluster, not by the threshold check itself.

stage 1c · mincut as a primitive

What CM asks VieCut to compute on each pop.

VieCut returns three things per call: the minimum cut size (an integer count of edges), the in-side node list (the smaller of the two halves the cut produces), and the out-side node list. The "minimum" qualifier is over all possible bipartitions of the cluster's nodes: the smallest edge count whose removal disconnects the cluster. The "most balanced" qualifier breaks ties: among all bipartitions achieving the minimum, VieCut picks the one whose two sides are closest in size.

Why minimum and not "weakest link" or "most central edge"? The minimum cut is the bottleneck of the cluster: removing fewer edges than the mincut leaves the cluster connected; removing the mincut edges disconnects it. The threshold check asks whether this bottleneck is wide enough. A yes verdict means the cluster is well-connected. A no verdict means the bottleneck IS where the cluster should be split. The CM design uses mincut both as the diagnostic (is the cluster well-connected?) and as the corrective (where exactly to cut?).

Two interesting properties of the mincut + balance criterion. The balance step is what keeps recursion depth low; without it, a "trivial cut" (one node on one side, n-1 on the other) would peel one node at a time and produce a recursion depth of \(n\) instead of \(\log n\). And the mincut bipartition is unique up to ties: if the cluster has exactly one minimum cut, both the cut size and the partition are unique. If multiple bipartitions tie, balance picks one, and the choice is deterministic given VieCut's internal state.

The "most balanced" criterion bears extra reading. Among all bipartitions achieving the minimum cut, the most balanced one is the partition whose two side sizes are closest. For a cluster of n nodes, the ideally balanced partition has sides of size \(\lfloor n/2 \rfloor\) and \(\lceil n/2 \rceil\). VieCut's balanced-cut-DFS algorithm searches the space of minimum-cut bipartitions and picks the one closest to this ideal. The search is exact (no heuristic approximation), so the choice is deterministic given the input and the RNG state.

Why balance matters operationally. On a cluster with a single bottleneck (one minimum cut), balance picks that cut and the two sides are however the bottleneck splits them. On a cluster with multiple minimum cuts (e.g. multiple edge-pendant attachments to a dense core, each a size-1 cut), balance picks the most balanced of those, which is the periphery pendant whose removal would leave the largest connected piece behind. On a cluster with no clear bottleneck (e.g. a dense graph with mincut equal to the minimum degree), balance picks among many ties.

cactus mincut, briefly

VieCut's cactus algorithm (Karger, Stein 1996; refined in Henzinger et al. 2018) builds a "cactus" auxiliary graph that compactly represents every minimum cut of the input. The CM kernel reads off one of those minimum cuts plus the cluster's bipartition. Cost is \(\tilde{O}(m \log^3 n)\) for the cactus construction plus \(O(m)\) for the balanced-cut readout. On the 32-node fixture, the mincut step is microseconds per pop. On networks with thousands of large clusters, mincut is the dominant cost of the CM stage.

stage 2 · cut + recluster rounds

Mincut, threshold check, base-algo recluster on each cut half.

This is Park 2024's stage 3, the CM loop. Each step is one queue pop: pull a cluster, run VieCut cactus mincut, check whether the cut clears the threshold for the cluster's size. Pass: the cluster joins the survivor set. Fail: the base algorithm re-clusters each cut half of size larger than one node, and the resulting communities push into the next round's mincut queue.

what a round does

A round drains to_be_mincut entirely. Each pop produces either a survivor (push to the survivor list, no further work) or a failed cut (run the base algorithm on each side of size larger than one, push each resulting community to to_be_clustered). Termination: a round produces no work for the next round.

the FIFO discipline

Both queues are first-in first-out. The order clusters enter to_be_mincut matches the order their connected components appeared in the seed step, and the order base-algo outputs land in to_be_clustered follows the order the base algorithm returned them. FIFO preserves the property that an output partition is fully determined by the inputs and the seed: rerun with the same inputs and you get the same partition, in the same order.

cost per pop, in three primitives

Three computations dominate the per-pop work. First, cactus mincut on the induced subgraph: VieCut's cactus algorithm runs in near-linear time over the cluster's edges, so on a cluster with \(m\) intra-cluster edges, the per-pop cost is \(\tilde{O}(m)\). Second, the threshold check: constant time per pop. Third, the re-cluster step on each failing side: Leiden CPM runs in time \(O(\text{vertices} + \text{edges})\) per iteration with two iterations per call, so for a side of \(m'\) edges the re-cluster cost is \(O(m')\). The whole CM stage cost is roughly \(O(M \cdot R)\), where \(M\) is the total number of intra-cluster edges across all rounds and \(R\) is the depth of the recursion tree. On well-behaved inputs \(R\) is small (a handful of rounds at most); on pathological inputs (every recluster returns the same single community) \(R\) can grow linearly with cluster size.

What the walker shows that the source code does not

The walker exposes three properties of CM that the source code does not make obvious. First, the lineage tree's shape is a function of base-algo behaviour, not just threshold behaviour. Source code reading suggests CM is "WCC plus a Leiden call"; the walker shows that the Leiden call is what determines whether the chain is linear or branching. A real-world example: what depth-20 looks like

On the bumped 3-tier stress panel's largest network (around 600k nodes), the deepest lineage chain observed has 20 levels. A length-20 chain means one input cluster spawned a descendant chain of 20 fresh ids, each round cutting and re-clustering down through successive smaller residuals.

Reading what produces depth 20: the input cluster is on the order of tens of thousands of nodes; the threshold function at that size is around 4 (\(\log_{10}(10000) = 4\)); the cluster's mincut is small (1, 2, or 3) and stays small as the cluster shrinks because the cuts peel off thin appendages rather than splitting the bulk. The base algorithm returns one community most rounds (the residual is internally similar to the parent), so the cluster shrinks by a small amount per round. Depth 20 is the result of 20 small-shrinkage rounds before the threshold finally drops below the cut.

The same pattern at smaller scale: the 32-node fixture's cluster A under low-resolution Leiden produces a depth-4 chain. The proportional shape is similar; what changes with scale is the chain length.

Why the chain length grows with cluster size. The threshold function \(\log_{10}(n)\) is monotone increasing, so larger clusters face higher bars. A cluster of 10000 nodes facing a mincut of 2 has threshold 4, so it fails by 2 edges. Each peel round removes one node from the cluster (the trivial 1 vs n-1 cut); the threshold drops by \(\log_{10}((n-1)/n)\), which for large n is very close to 0. So the cluster has to shrink by many rounds before the threshold drops by an integer-sized amount. Concretely: a cluster of 10000 nodes with mincut 2 has to shrink to about 1000 nodes (threshold 3, fails by 1) and then to 100 nodes (threshold 2, ties: still fails by epsilon) and then to 99 nodes (threshold below 2, passes). The peel chain is approximately \(n / 10\) long at this regime.

On real empirical networks the chain length is bounded by the recluster step's ability to find sub-communities. When the base algorithm starts producing multiple communities per side (instead of one), the chain branches into multiple shorter chains, each on a smaller side. Branches stop the chain length from growing linearly in cluster size; the depth-20 maximum on the bumped 3-tier panel happens because some clusters do not branch at all and have to peel one node per round.

why the re-cluster output drives the trajectory shape

Reading the three rows side by side: CM's behaviour depends on (a) whether the threshold catches the cluster at all and (b) what the base algorithm produces on each cut half. The threshold gates the loop's entry; the base algorithm shapes the loop's branching. When both knobs say "do something", CM does the heaviest version of its job; when either says "do nothing", CM short-circuits in different ways. The threshold determines whether CM cuts; the base algorithm determines what CM does after the cut.

stage 4a · what guarantees termination

The CM loop is not formally proven to halt; reading why it usually does.

The recursion in CM is not size-monotone in the strict sense. A cluster fails the threshold, the base algorithm re-clusters each side, and the re-cluster output can in principle be the same single community on a side just as large as the failing cluster. If that happened repeatedly, the loop would run forever. Three forces conspire to make termination practical.

First, the threshold drops as the cluster shrinks. Every cut peels at least one node off (one side has size 1 or more, the size-larger-than-one gate filters singletons, so the surviving descendants are strictly smaller than the failing cluster). The threshold \(f(n)\) is monotone increasing in \(n\), so smaller residuals face a lower bar. Eventually the threshold falls below the mincut value and the cluster passes.

Second, the base algorithm usually does shape the cut. Leiden CPM at non-trivial resolution returns multiple communities per side most of the time; each community is smaller than the failing side. The lineage tree branches and the work spreads across many smaller clusters, each of which faces a lower threshold. The "single chain, one peel per round" trajectory seen on cluster A is the exception, not the rule, on real inputs.

Third, the singletons-die-after-one-round invariant. Even when the re-cluster step produces singletons, the binary pushes them into to_be_clustered without filtering. The next round's mincut on a 1-node graph returns cut=0 against any positive threshold, the cluster fails, the re-cluster on a 1-node side is filtered by the size-larger-than-one gate, and the singleton vanishes. Net: a singleton sits in the queue for at most one extra round, then is gone.

Together these forces bound the recursion depth for any realistic input. The pathological case (a base algorithm that always returns one community on every side, on a fixture where the threshold never falls below 1) would loop, but no such case has been observed on the stress matrix or on the empirical networks studied in Park 2024. The implementation does not include an explicit loop counter; the Python wrapper has a safety timeout, but the binary itself does not.

One subtle property of the termination behaviour is that it depends on the base algorithm's locality. The base algorithm sees one cut half at a time, not the whole graph. So even if the base algorithm has a global preference for one large community (low-resolution CPM, say), its decision on a 200-node side may differ from its decision on the original 1000-node cluster, because the smaller induced subgraph has a different optimum. CM exploits this locality: the base algorithm's behaviour on a smaller cluster is what makes the recursion converge, not the algorithm's behaviour on the global graph.

A formal termination proof would require characterising the base algorithm's behaviour on every possible induced subgraph, which is not generally tractable. The empirical termination claim is sufficient for the gallery's purposes: across 600+ networks and 50+ seeds, no CM run has failed to terminate within the wrapper's timeout. Anyone running CM on a new network will probably see termination too; the worst case is bounded by linear recursion depth in cluster size.

recursion depth in practice

On the bumped 3-tier stress panel (161 empirical networks, sizes from 34 nodes to 600k+ nodes), the deepest lineage chain observed is around 20 levels on the largest networks. Most input clusters have depth 0 (extant) or depth 1 (one round of cut + recluster). Depth grows logarithmically with cluster size when the base algorithm cooperates, linearly when it does not. The mean depth across all inputs is below 2.

three sufficient conditions for termination

The recursion terminates under any of three sufficient conditions, even though none is required for every run. First: the threshold function tends to 0 as \(n \rightarrow 1\), so any cluster eventually shrinks below the bar (logically: as cluster size approaches 1, the threshold approaches 0, and a cut of 1 is trivially above 0). Second: the base algorithm returns smaller communities than the input on at least one round, breaking the chain. Third: the singleton-filter property guarantees that any size-1 cluster dies after one extra round, so the queue cannot grow without bound from singletons. The first condition is the most general; the other two are stronger but rarer in practice.

what would break termination

A pathological input: a fixture where every cluster has mincut 1, every cut peels off one node only, and the base algorithm returns the same single community on every cut side. Under those conditions the loop peels one node per round forever (until the cluster reaches the threshold's zero-crossing). The recursion depth bounds at \(n - 2\) (the cluster shrinks one node per round; the last reduction brings it to size 2, after which mincut 1 vs threshold \(\log_{10}(2) \approx 0.301\) lets the cluster pass). So even the pathological case has bounded depth, just linear in cluster size. No real network is observed to hit this; the empirical worst case is around 20 levels deep.

stage 4b · queue invariants

Six things that hold at every round boundary.

The CM loop has a small set of invariants that make the trace readable. Listing them helps when the lineage tree gets deep and the per-round counts grow.

  • Every queue entry has a unique cluster id. The id counter next_cluster_id only increases. No id is ever re-used, so the lineage tree has no cycles.
  • Node sets across the three queues are disjoint at any given time. A node sits in exactly one of to_be_mincut, to_be_clustered, or the survivor list at any pop boundary. The seed step partitions all clustered nodes among queues; later pops shuffle them between queues without ever duplicating or dropping (except for singletons that are filtered).
  • Within-cluster node ids are sorted ascending. The seed step's BFS produces node-id-ASC components; the std::set conversion at emit time preserves ASC; the recluster step's translation preserves ASC. Reading any queue entry, the node list is sorted; this matters for the byte-equal verification to canonical.
  • parent_to_child[-1] holds every input cluster that ever fragmented. The root row of the lineage tree records the set of original cluster ids that lost an unmodified component. Scanning the root row tells you which input clusters CM touched at all.
  • Rounds are FIFO across the boundary. Cluster X enters to_be_clustered at the end of round R; it appears in to_be_mincut at position equal to its push order at the start of round R+1. No reordering.
  • Termination: a round whose end finds to_be_clustered empty stops the loop. Equivalent statement: every cluster in the most recent round either survived (added to survivor list) or got cut into singletons (filtered). No further work pending.

These invariants make the trace deterministic given the seed: rerun on the same input with the same seed and you get the same lineage tree in the same order. Two interesting consequences. The walker's per-round state is fully determined by the events emitted so far, so scrubbing back and forth in the player is exact, not approximate. And the lineage tree's depth equals the number of rounds the cluster's lineage chain survived, which gives a direct read of how aggressively CM modified each input.

stage 5 · cluster fate dictionary

Four labels Park 2024 §4.2 reads from the lineage tree.

Each input cluster ends up labelled with one of four fates. The fate is reconstructable from the lineage tree alone, which is why the binary writes the tree to disk; the fate labels themselves are computed by a separate analysis pass.

extant

One child, same id as parent. The cluster passed every threshold check; it shows up in the output unchanged. On the 32-node fixture under \(\log_{10}\): B, C1, C2, D. The fixture's "easy" clusters.

reduced

One child, smaller node set. Either the prune branch peeled nodes off, or the post-CM size filter dropped some pieces. On the 32-node fixture under \(\log_{10}\) without prune: A's lineage \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\) ends at 9 nodes, down from 12. The output is "A's reduced form".

split

Two or more children. The base algorithm's re-cluster returned multiple communities on at least one cut half, or the seed step started with multiple components for one input cluster id. C on this fixture is the seed-step split: input cluster id 2 fragments into the two 3-cycles before the mincut loop runs.

degraded

Every leaf descendant ends up below the post-CM size filter \(B\) (default 11). The cluster is effectively erased; what remains is fragments small enough that the wrapper drops them. This fate only appears when the size filter is applied, which is in the Python wrapper, not the binary itself. The walker above does not apply \(B\), so this fate does not surface on the 32-node fixture.

The four labels are exhaustive and disjoint per input cluster. Park 2024 §4.4 reports fate distributions across the five base algorithms studied: under Leiden-CPM at low resolution, the share of "split" + "reduced" is large; under IKC at k=10, most clusters are "extant"; Leiden-Mod sits in between. The reader looking at a CM output partition can read the lineage tree to find out which input clusters were touched and how.

Reading a lineage tree row

A row in history.log has the form parent:child1,child2,.... The "-1" row lists every input cluster id that was ever fragmented (one or more pieces did not equal the entire input cluster); the rest of the rows trace the modifications. Reading the tree as a whole, the depth gives a structural summary: input clusters that ended up extant have depth 0 (their id never appears as a parent in any row), reduced clusters trace a chain (depth equals the number of single-child rounds), split clusters fan out (a node with multiple children), and degraded clusters fan out and then every leaf falls under \(B\). The lineage tree is compact enough that even on networks with thousands of input clusters, the per-fate breakdown is computable in one linear scan.

Mixed fates within one input cluster

The four fates are per input cluster, but the per-leaf outcomes within one input cluster can be mixed. A "split" fate can mean two survivors plus one dropped singleton plus one degraded fragment. The fate label captures only the structural shape; the detailed per-leaf outcomes are read off the lineage tree by inspection.

A worked example. Suppose input cluster X (n=200) is split by CM into three children: X1 (n=120, extant), X2 (n=40, reduced further to a 25-node survivor), X3 (n=40, every descendant ends up below \(B\)). The fate of X is "split" (multiple children), and within that split, one child is "extant", one is "reduced", one is "degraded". The lineage tree records the full chain; the fate analyzer reads the chain to produce summary statistics.

Reading per-fate counts: in Park 2024 Table 2, the column "split" counts input clusters with more than one child; "reduced" counts those with exactly one smaller child; "extant" counts those with exactly one same-sized child; "degraded" counts those whose every descendant fell below \(B\). The four columns sum to the number of input clusters, and the per-row totals are the dominant signal: a Leiden-CPM r=0.0001 input has a large "split" + "reduced" share; an IKC k=10 input has a large "extant" share.

When degraded is the dominant fate

The "degraded" fate is interesting because it represents complete erasure of an input cluster from the output. Every descendant ends up below \(B\), so the post-CM size filter drops them all, and the cluster contributes nothing to the final partition. This happens when (a) the input cluster was a tree-like structure with low internal connectivity, (b) the threshold failed it at every recursion level, and (c) the base algorithm could not find any well-connected sub-community larger than \(B\).

Park 2024 reports degraded clusters concentrate on Leiden-CPM at low \(r\) inputs where the resolution is so low that even the largest cluster's internal sub-structure is below \(B\). The degraded share scales inversely with \(r\): higher resolutions produce smaller clusters that pass the threshold easily; lower resolutions produce large clusters that fragment into below-\(B\) pieces.

The implication for downstream analysis: a "degraded" fate is a signal that the input partition over-merged at scale. The cluster's structure was so fragmented under the threshold's gaze that nothing survived. Reading the per-fate distribution on a CM run gives a quick diagnostic for "is the base algorithm operating in a regime that suits this network's structure?". A high degraded share is a hint to try a higher resolution or a different base algorithm.

Reading the fate distribution as a partition-quality signal

Park 2024 §4 frames the cluster fate distribution as an indirect measure of input partition quality. The reasoning: a high-quality input partition has clusters that are already well-connected, so most fates are "extant" and few are "split" or "degraded". A low-quality input partition has clusters that need correction; fates skew toward "split" and "degraded". The distribution is read together rather than per-fate.

Three regimes to recognise. High extant share. The input partition was already well-connected; CM did little. Likely the base algorithm was well-tuned (high resolution, structurally aware) for this network. Mixed split + reduced share. The input partition had medium-quality issues; CM peeled off bad pieces and re-clustered the rest. Likely the base algorithm was operating in a default regime. High degraded share. The input partition over-merged severely; CM modified or erased most clusters. Likely the base algorithm's resolution was too low for this network.

Two interesting properties of this signal. The fate distribution is base-algorithm-aware in the sense that "degraded" and "extant" mean different things across base algorithms (degraded under IKC is suspicious because IKC is conservative; degraded under Leiden-CPM at low r is expected). And the fate distribution depends on the threshold function: under a stricter threshold (\(\sqrt{n}\) above n=100), more clusters fail and more fates skew to non-extant. Reading the distribution requires holding the threshold and base algorithm fixed for comparison.

The B cluster is the case CC misses

B is two K4's joined by a single bridge edge (between nodes 15 and 16). The shortest description of B's structure: two dense communities of four nodes each, connected by one thin link. CC sees B as one connected component and leaves it alone. WCC and CM both check B's mincut: cut = 1 (the bridge), threshold = \(\log_{10}(8) \approx 0.903\). Strict inequality \(1 > 0.903\) holds, so B passes. B is well-connected by the criterion's definition, even though intuitively it looks like two communities.

This is a feature of the threshold's mildness. The log default is set permissive enough that small clusters with a single internal bridge still pass, on the logic that requiring cluster cohesion at the smallest cluster sizes throws away too much information. The threshold is designed for the regime where clusters span tens to thousands of nodes; at \(n = 8\), the bar is below 1, so any cut value of 1 or higher passes. The price is that this fixture's B cluster, which a human reader would call "obviously two communities", passes the test.

Under the stricter \(2 \cdot \log_{10}(n)\) variant, B's threshold becomes 1.806, and the cut of 1 fails. B gets cut along its bridge, and the re-cluster step runs on each K4. Leiden-CPM on a K4 at r=0.0001 returns one community (its CPM optimum is one cluster for a dense input). The two K4's emerge as separate survivors. Reading the trace: the threshold choice is what determines whether B is one cluster or two. The algorithm itself does not have an opinion.

The C cluster shows the seed-step split

C is two disjoint 3-cycles labelled with the same input cluster id. The two 3-cycles share no edge between them; they are two connected components under the same label. CC's seed step is what catches this: drop cross-cluster edges (none here, since both 3-cycles carry the same id), take connected components of the residual, and the two 3-cycles emerge as separate components.

The lineage id assignment then takes over. The first component (in component-id ASC order, which corresponds to node-id ASC within each component) keeps the original cluster id (id 2 in the fixture). The second component gets a fresh id from the counter. Both components push to to_be_mincut. The mincut + threshold loop sees them as two separate clusters from the start; whatever happens next is independent for each.

On this fixture, both 3-cycles are 2-edge-connected (cycle of length 3 has mincut 2), threshold \(\log_{10}(3) \approx 0.477\), so 2 > 0.477 holds and both pass on the first check. Output: two survivors, C1 and C2. Fate of input cluster 2: "split" (two children, distinct ids). The split happened at the seed step, not during the cut-recluster loop. CM's behaviour on C is identical to WCC's and to CC's: the seed step does all the work.

This is one place CM's stage-1 behaviour is observable in isolation. The 32-node fixture's C cluster is the seed-step case for all three post-procs; on networks where input clusters can be internally disconnected (a common SBM output), the seed step is non-trivial and the first round of mincut sees the components, not the original clusters.

The seed step's contribution is sometimes the dominant change to the partition. On SBM outputs that label disconnected blocks with the same id, the seed step splits more clusters than the cut + recluster loop. The threshold check often passes for the resulting components because each is small enough that the threshold falls below the cluster's mincut. So CM's final output equals "input partition's CC-split form" on such inputs; the modify-or-recluster loop is a no-op. The walker still emits round-0 events for every queued cluster, but none of them fail the threshold.

When the three post-procs disagree

On most empirical networks, CC and WCC and CM disagree on a small fraction of clusters. The disagreement is concentrated where each post-proc adds something the previous one does not have. CC and WCC disagree on clusters with mincut 1 (CC keeps them; WCC cuts them under \(\log_{10}\)). WCC and CM disagree on clusters that fail the threshold AND have base-algo-discoverable sub-structure (WCC produces two halves; CM produces however many communities the base algorithm finds).

On the bumped 3-tier stress panel under Leiden-CPM at r=0.0001, the disagreement rate between WCC and CM is on the order of 20-30% of input clusters: roughly that many clusters fail the threshold AND the base algorithm finds sub-communities the cut would not have. Under Leiden-CPM at r=0.5, the rate drops below 10%, because the base algorithm's clusters at high resolution are already internally cohesive.

Reading the disagreement rate as a partition signal: a high rate means the input partition over-merged at the small-cluster level (the base algorithm at low resolution did not see real sub-structure); a low rate means the input partition was already close to what the base algorithm would produce on each cut half. The rate is itself a function of the threshold function and the base algorithm choice, so comparing across runs requires holding those fixed.

Three observations about the spectrum

Looking at CC, WCC, and CM as a spectrum of intervention strength surfaces three observations worth stating explicitly.

Coverage grows, partition gets smaller. CC produces the largest output partition (it only splits, never drops); WCC produces a smaller one (it drops singletons that emerge from cuts); CM produces the smallest (it drops singletons plus any community the base algorithm decides to fragment). Node coverage drops correspondingly: CM has the lowest node coverage of the three.

Cluster sizes shift down. CC keeps the input cluster sizes (it only splits into multiple smaller); WCC shrinks them further (cuts trim periphery); CM shrinks them most (cuts plus re-cluster trim further). The CM output partition's size distribution is shifted left (toward smaller clusters) relative to the input.

Output cluster count usually grows. Each cut creates two clusters from one (modulo singletons that get filtered). So the post-CM cluster count is usually higher than the input. The exception is when many input clusters degrade entirely (every leaf below \(B\)); under that condition, the output count can be lower than the input. The cluster fate distribution describes which case applies on any given input.

stage 6 · edge cases

What CM does at the corners.

leiden returns the same partition

The base algorithm is a fixed point on its own quality function, so a re-cluster can return one community spanning the whole input side. CM pushes that single community back into to_be_clustered; next round it will be mincut again. CM has no explicit guard against this, so a pathological input could loop. In practice Leiden CPM at low resolution converges, and the threshold eventually accepts a sufficiently large component as well-connected once \(n\) drops below the criterion's crossover.

cluster disintegrates into singletons

A re-cluster on an n-node side can return n singleton communities. Singletons of size 1 still get pushed into to_be_clustered in the binary (the canonical does not filter at this site), then the next-round mincut on a size-1 cluster is trivial (cut = 0, threshold > 0, well-connected = false), so they re-enter the recluster step on a size-1 side, which IS filtered by the size-larger-than-one gate, and never come back. The singletons die after one extra round, not an infinite loop. The pipeline then applies a post-filter (size ≥ \(B\) = 11 by default) at the end, which removes any small surviving fragments. That filter is Park 2024's stage 4.

threshold equals cut exactly

The strict comparison with a 1e-9 tolerance resolves cluster-at-the-threshold to not well-connected (push back). A cluster sitting exactly at the threshold gets re-cut and re-clustered. The bias is intentional: the post-proc's job is to find under-cohesive clusters, and an equality at the boundary is closer to "fails" than "passes".

disconnected input cluster

The seed step splits any input cluster that is internally disconnected, before the mincut loop sees it. Each piece gets its own lineage id (or keeps the original id if exactly one piece equals the entire input cluster). The fate label for the original input is "split" with the pieces as children; if any piece is later modified further, the tree deepens. On the 32-node fixture, C is the disconnected input: two 3-cycles labelled with the same id. CM finds both at the seed step and never has to mincut C.

tree-shaped cluster

A tree has mincut = 1 by construction (every edge is a bridge), so every tree cluster fails the threshold at any \(n \geq 2\) under \(\log_{10}\). The recursion peels one edge at a time and the cluster effectively melts. Park 2024 §3 adds a pre-stage that filters tree clusters before stage 3 to avoid spending compute on them; that filter lives in the Python wrapper, not the binary.

empty side after cut

If VieCut returns a degenerate cut where one side is empty, the size-larger-than-one gate skips it and the round proceeds with whatever it has. In practice cactus mincut on a connected graph of \(n \geq 2\) nodes always returns two non-empty sides, so this case does not arise on real input.

tied mincut, multiple balanced cuts

VieCut breaks mincut ties by picking the most balanced cut (the option that splits the cluster roughly in half rather than peeling one node off). The balance criterion matters: an unbalanced tie-break would peel one node at a time and stall the recursion, since each subsequent round would face a cluster only one node smaller. The most-balanced choice makes each round halve (roughly) the problem size, so the recursion depth stays \(O(\log n)\) in the worst case. The tie-break itself is deterministic given the same input: VieCut's DFS-based balanced-cut algorithm has a fixed traversal order, so two runs on the same induced subgraph produce the same bipartition.

VieCut RNG state drift across pops

VieCut is deterministic given its RNG state at the start of each mincut call. The state is seeded once at binary startup and not re-seeded per call (the intended per-call re-seed is commented out in the source). Two pops on identical induced subgraphs at different points in the binary's run can produce different mincut outputs if the random draws between them happened to land on different state values. The JS port mirrors this exactly: its MT19937 state is shared across pops within a single CM run. The byte-equal verification chain has to reproduce this drift, not just the initial seed.

multi-threading: ids stable, partition stable, order not

Under --num-processors greater than 1, worker threads pull from the FIFO concurrently, and the assignment of fresh ids to drained clusters depends on which thread pops first. The output partition (the node sets of each cluster) is stable under multi-thread; only the cluster id labels and the row order of com.csv vary across runs. Under --num-processors 1, both partition and labels are stable; two runs on the same input produce byte-identical output. The verification harness pins to single-thread for that reason.

re-cluster returns multiple disconnected sub-communities

The base algorithm can return a community whose internal subgraph is itself disconnected. Louvain has this property without refinement; Leiden's refinement phase prevents it for Leiden outputs. CM handles the case generically: after the base-algo call, run RemoveInterClusterEdges + GetConnectedComponents on the side's induced subgraph, which splits any disconnected returned community into its connected pieces. Each piece is pushed to to_be_clustered separately. Under Leiden this is a no-op; under Louvain it can add work.

very small clusters bypass the loop

A cluster of size 2 (one edge) has mincut 1 by construction. Under \(\log_{10}(2) \approx 0.301\), 1 > 0.301 holds and the cluster passes. Under \(2 \cdot \log_{10}(2) \approx 0.602\), 1 > 0.602 holds and the cluster passes. Under \(1 \cdot \log_2(2) = 1.0\), the cluster ties; with the epsilon guard it fails. So size-2 clusters under stricter thresholds get cut into singletons that vanish. This is a small but visible effect on partitions with many size-2 clusters as a base-algorithm artifact.

base-algo crashes on degenerate input

The re-cluster step calls Leiden on the induced subgraph of one cut half. If the side has zero edges (all isolated nodes), Leiden returns one community per node, all singletons. CM's connectivity-component pass then sees one component per node, each pushed to to_be_clustered. The next round drops all singletons via the size-larger-than-one gate. Functionally a no-op, but the round counter does tick. No crash; just one wasted round.

criterion = "0" disables CM

Setting --connectedness-criterion 0 makes the threshold always 0; any cluster with cut > 0 (i.e. any connected cluster) passes the check. CM degenerates to the seed step plus the threshold check at the seed step (which every connected cluster passes). The output equals the input partition's CC-split form, identical to what CC would produce on the same input. This is a documented behaviour, not a degenerate case; "criterion = 0" is the way to run the binary in CC mode.

criterion = piecewise (the binary's custom variant)

The binary supports a "piecewise" criterion that returns banded thresholds by cluster size: \(n < 100\) requires cut \(\geq 1\), \(100 \leq n \leq 500\) requires \(\geq 2\), \(500 < n \leq 999\) requires \(\geq 3\), \(n > 999\) requires \(\geq \lceil \sqrt{n}/10 \rceil\). The piecewise variant is an integer-valued bar (no FP rounding), so the epsilon guard is a no-op for it. The walker exposes this criterion as a dropdown option on the WCC page; CM's criterion dropdown also supports it via the same parser.

stage 7 · what feeds CM

Base partition sources exercised in the stress matrix.

CM is a post-processor by definition: it modifies an existing clustering. The choice of base partition matters because CM's gain (or non-gain) depends on how well-connected the base algorithm's clusters already are. The byte-equal verification chains CM against four base partition sources, plus two base re-clusterers (Leiden-CPM at two resolutions, Leiden-Mod). Together they span the regime where CM helps and the regime where CM is a no-op.

Leiden-Mod

The libleidenalg ModularityVertexPartition. Maximises Newton-Girvan modularity. Subject to the well-known resolution limit: small communities get merged into bigger ones. CM tends to split those merged blobs.

Leiden-CPM r=0.5

High-resolution CPM. Produces small dense clusters. CM mostly leaves these extant; the threshold is easy to clear for clusters that are already small and dense.

Leiden-CPM r=0.0001

Low-resolution CPM. Produces large clusters that bundle real sub-communities. CM aggressively peels and re-clusters. This is the regime where CM provides the most empirical lift.

SBM-Flat-PP

Planted-partition stochastic block model output. Block boundaries by construction; the input partition is internally consistent. CM's role here is mostly a sanity check that the post-proc does not over-modify a healthy input.

The empirical reading from Park 2024 §4.4: the more the base algorithm over-merges, the more CM splits; the more the base algorithm over-splits, the less CM has to do (and the small overhead of running mincut + re-cluster on every cluster still happens). CM is not a free correction. The Python wrapper's size filter \(B = 11\) bounds the cost downstream by dropping fragments below the threshold.

How CM's behaviour reads across base-algorithm regimes

CM cleans up a base algorithm's output by removing clusters that look connected on paper but have weak internal structure. Three rough regimes describe CM's typical behaviour:

The over-merge regime. Leiden modularity has the resolution limit; SBM-Flat-PP can merge blocks when the input clustering is coarser than the underlying structure; Louvain with no refinement can produce disconnected communities. In any of these cases, CM has clear work to do, and the post-CM partition is meaningfully different from the input.

The conservative regime. IKC k=10 produces 10-edge-connected clusters by construction; Leiden CPM at high resolution produces small dense clusters; SBM-Nested-Best fits multiple resolutions and the smallest fit may already be well-connected. In these cases CM has little work to do, and running CM adds runtime overhead with no partition change.

The diagnostic reading. The cluster-fate distribution is itself a diagnostic. A high "extant" share means the input was already well-connected; a high "split" share means CM caught something the base algorithm missed; a high "degraded" share means the input was so badly over-merged that even after splitting, nothing usable survived above \(B\).

The three post-procs span a spectrum. CC is the cheapest correction; CM is the most aggressive. The cost dimension is compute (CC is one BFS per cluster; CM adds mincut + a base-algo call per failing cluster). The catch dimension is what each catches: CC catches disconnected clusters; WCC adds thin-bridge clusters; CM adds whatever else the base algorithm flags as suspect when given one cluster at a time.

What each chain partner is good at and what it misses

The five chain partners (four base partition sources, two re-clusterer choices) cover the regimes where CM matters most. A short profile of each.

Leiden-Mod as a base partition. Leiden optimising modularity tends to produce large clusters at the resolution limit. On networks with a wide range of community sizes, the smallest real communities get merged into bigger ones because modularity rewards merging when the merger increases the global score, regardless of whether the merged unit makes sense locally. CM finds those forced merges and splits them along the weakest internal connection.

Leiden-CPM at low resolution as a base partition. CPM's "constant Potts model" objective is parametrised by a resolution \(r\). At low \(r\) the model rewards large clusters; at high \(r\) it rewards small ones. Park 2024 ran CM on Leiden-CPM at \(r \in [0.0001, 0.001]\) and showed CM produces large gains in that regime, because the base algorithm is blind to internal connectivity at those resolutions and CM does the corrective work.

Leiden-CPM at high resolution as a base partition. The opposite regime. CPM at \(r = 0.5\) and above produces small dense clusters; the threshold \(\log_{10}(n)\) is low for those sizes, so most clusters pass on the first check. CM is close to a no-op here; the stress matrix's high-resolution panel is mostly extant-fate outputs.

SBM-Flat-PP as a base partition. The planted-partition stochastic block model produces partitions where block boundaries are by construction. The input is internally consistent: blocks are well-connected within and weakly-connected across. CM's role is sanity check that the post-proc does not over-modify a healthy input. Empirically: a few clusters fail on edge cases (small blocks with unlucky sampling), most pass.

Infomap as a base partition. Infomap's map equation rewards clusters that contain random-walk-coherent regions. The clusters tend to be structurally motivated rather than density-motivated; some pass the threshold, some do not. CM intervenes more than on Leiden-CPM at high resolution but less than on Leiden-Mod. Infomap is in the binary's algorithm choices but not in the wrapper's accepted base-algo list, so today's deployed CM does not chain through Infomap; the gallery's stress matrix still includes it as a chain partner for verification breadth.

IKC k=10 as a base partition. IKC produces clusters of k-edge-connected nodes by construction (every cluster has mincut at least k). For k=10, the threshold function \(\log_{10}(n)\) is below 10 for any \(n \leq 10^{10}\), so every IKC cluster passes the threshold trivially. CM is a near-no-op on IKC output; Park 2024 §4.4 reports this is the case where CM provides the least lift. IKC's structural guarantee is upstream of CM's job; clusters that are already 10-edge-connected do not need CM to confirm so.

A digression: why Leiden refines and Louvain does not

Leiden has a refinement phase after each round of node moves that Louvain lacks. The refinement phase splits a community into sub-communities if doing so increases the quality, then optionally re-merges. The net effect is that every Leiden output community is internally connected: there is no community whose induced subgraph has more than one connected component. Louvain has no such guarantee; a Louvain output community can be disconnected if the node-move sequence happens to leave it that way.

For CM's re-cluster step, the difference matters. After the base algorithm returns its partition, CM runs RemoveInterClusterEdges + GetConnectedComponents to split any disconnected community into its pieces. On Leiden output, the CC pass usually does nothing because Leiden's communities are already connected. On Louvain output, the CC pass can fragment a community further, adding more entries to to_be_clustered than the base algorithm intended. The CM cost grows correspondingly.

The wrapper supports Leiden CPM, Leiden Mod, and Louvain; the byte-equal verification covers Leiden CPM (at two resolutions) and Leiden Mod. Louvain is in the binary but rarely deployed; the gallery's stress matrix does not yet include Louvain as the re-clusterer. The reason is the disconnectedness behaviour: Louvain plus CC produces more queue churn than Leiden, and the verification harness has not been re-run for the Louvain case in this gallery cycle.

A note on the RNG streams CM consumes

CM has two independent RNG streams. The first is VieCut's mincut RNG: libstdc++ MT19937, seeded once at binary startup, state drifts across pops. The second is the base algorithm's RNG: igraph's MT19937 (via libleidenalg for Leiden, via igraph's bundled implementations for Louvain and Infomap), re-seeded to 0 on every call. The two streams do not interact; a change in one does not affect the other.

The choice of "re-seed per call" for the base algorithm is deliberate. Each re-cluster step is supposed to be a function of the side's induced subgraph alone, not of the order of CM's pops. Re-seeding gives that property: two CM runs that happen to re-cluster the same induced subgraph at different pop positions get the same Leiden output. The cost is that the base algorithm's RNG state does not get to "warm up" across CM rounds, but on the small graphs the base algorithm sees per call, this matters less than the determinism gain.

VieCut's behaviour is the opposite. The mincut RNG state carries across pops, so two mincut calls on identical induced subgraphs at different points in the run can produce different bipartitions (when ties exist; the cut size itself is deterministic from the input). This is a quirk of VieCut's design rather than a CM choice; the CM kernel just reads whatever VieCut returns. The byte-equal verification handles it by chaining through VieCut explicitly.

Why mincut as the diagnostic, not modularity or CPM directly

An alternative design would re-check the base algorithm's quality function on each cluster: a cluster passes if it is a local optimum of modularity (or CPM), fails otherwise. Park 2024 chose mincut + threshold instead. The reasoning is structural rather than algorithm-specific. Mincut measures internal connectivity, which is a property of the cluster's subgraph alone; modularity and CPM measure something else (the optimality of the cluster relative to the rest of the network), and they conflate "the cluster is internally cohesive" with "the cluster fits the network's null model". A cluster can be a local modularity optimum and still have a thin bridge inside it; mincut catches that case where modularity does not.

The complement also matters. Mincut is base-algorithm-agnostic: the same threshold function applies regardless of whether the input came from Leiden, Louvain, Infomap, IKC, or SBM. The mincut + threshold framework is a uniform diagnostic across the whole gallery; the modularity-vs-CPM-vs-codelength distinction is upstream of CM, and CM does not care about it. Two algorithms can produce the same partition and have different quality scores; CM treats them identically.

Tracing one divergence: the pre-prune that lives in Python

Park 2024 §3 specifies a pre-prune that iteratively removes every node with degree below \(f(n)\) inside the cluster, before any mincut runs. The binary's --prune flag implements a partial version (only the singleton-trivial-cut variant, where one side of a cut is a single node); the full degree-band prune is in the Python wrapper.

What the full pre-prune does: scan every node in the cluster, compute its degree within the cluster's induced subgraph, drop any node whose degree is at most \(f(n)\). Repeat until no node falls below the threshold. This shrinks the cluster from the periphery inward, removing the "easy targets" the mincut would otherwise find.

What the binary does instead: skip the pre-prune. Run mincut on the full cluster. If the cut is trivial (one side is one node) and the cluster is not yet well-connected, optionally remove the singleton via --prune and retry. The binary's variant catches only the cases where a single low-degree node would be peeled off; the full variant catches every low-degree node in one sweep.

Why the difference matters: on a cluster with many low-degree periphery nodes, the binary's per-cut peel is slower (one mincut per peel) than the wrapper's degree scan (one sweep total). On the 32-node fixture's cluster A, the wrapper's prune would identify nodes 5, 6, 7, 11 as below \(\log_{10}(12) \approx 1.079\) in one sweep (each has degree 1 inside A), drop them, and the residual 8-node cluster (the K5 plus three nodes) would then face a different mincut. The binary's per-cut peel requires three iterations of mincut to reach the same residual. Functionally, the wrapper's prune is the optimisation; the binary's is the slower fallback.

The walker above runs the binary's stage 3 only, so the pre-prune does not appear. The Python wrapper's full prune can be reproduced by computing the degree distribution within each cluster before the first mincut and dropping nodes below threshold, then running the walker on the pruned input. The walker does not do this automatically.

The Python wrapper's other duties

The Python wrapper around the binary handles several pre- and post-processing steps that affect what CM ends up doing on a real input. Listing them so the binary's behaviour can be situated:

Pre-CM size filter. The wrapper drops every input cluster of size below \(B = 11\) before passing the partition to the binary. The binary never sees those clusters; they pass through to the output unchanged.

Pre-CM tree filter. The wrapper identifies tree-shaped clusters (mincut = 1 trivially because every edge is a bridge) and drops them too. The binary never sees them; they pass through to the output unchanged.

Pre-CM degree-band prune. The wrapper computes per-node degree within each cluster's induced subgraph, drops nodes with degree at most \(f(n)\), repeats until stable. This is Park 2024's stage 3 pre-prune, applied at the wrapper level. The binary receives the pruned clusters as its input.

Post-CM size filter. After the binary returns, the wrapper drops every survivor cluster of size below \(B = 11\). The "degraded" cluster fate is computed here: an input cluster whose every descendant ended up below \(B\) becomes degraded.

Cluster fate analysis. The wrapper reads history.log, computes the per-input-cluster fate, and emits a fate distribution report. The binary writes only the raw lineage tree.

Together, the wrapper and the binary implement Park 2024's four stages. The binary handles stage 3 (the modify-or-recluster loop). The wrapper handles stages 1, 2, and 4 plus the cluster-fate analysis. The split makes the binary fast (it does only the heavy compute) and the wrapper flexible (it does the data wrangling). The walker on this page mirrors the binary's stage 3; the wrapper-side steps are described here for completeness but not exercised in the walker.

One more piece worth noting: the wrapper passes through the SLURM environment. The binary is designed to run under HPC schedulers; the wrapper's SCRIPT_DIR detection adjusts when running under SLURM. This means the binary itself does not assume a particular runtime environment; the wrapper handles cluster vs local invocation. Anyone running CM as part of a larger pipeline (research workflows often involve SLURM batch jobs across thousands of networks) gets the wrapper's environmental adaptation for free.

The --keep-state flag in the wrapper preserves intermediate files (the cm.log and history.log in the .state directory) after a run. Without the flag, the wrapper cleans them up after extracting the cluster fate distribution. The walker has no equivalent: every state it computes is in-memory only, and re-running the walker rebuilds the state from scratch.

a smaller point: the leiden inner iter count

The binary's re-cluster step runs Leiden twice per call: for i in [0, 2): optimise_partition(part). The first call builds a partition from a singleton init; the second call refines from the first call's output. Both calls share one RNG instance, so the second call's RNG state is whatever the first call left. The JS port re-seeds the MT19937 before each call, which is a small RNG-stream divergence; the verification tracer compensates by re-seeding on the canonical side too. End state matches.

VieCut's seed-once and the state-drift it implies

VieCut's RNG is seeded exactly once at the start of the binary's main, then left to drift. Every mincut call within a single binary run draws from wherever the previous mincut left the state. The intended per-mincut re-seed in mincut_custom.cpp is commented out, so the binary's behaviour is: same input, same seed, same mincut sequence; different ordering of clusters in the queue, different mincut RNG state per cluster. This state drift is one of the reasons the byte-equal verification chains through VieCut explicitly: the JS port has to reproduce the same drift across pops, not just the same initial seed.

What a record looks like, and why there are so many of them

Per pop, the verification harness records: round number, parent cluster id, current cluster id, cluster size, cut value, threshold (as a uint64 bit pattern, not as a decimal, to catch FP rounding mismatches), in-side size, out-side size, well-connected verdict, plus the re-cluster output structure if the cluster failed. Per round-end, the harness records: round-end signal, queue size, fresh ids assigned, lineage tree snapshot. Per Leiden call, the harness records the per-iteration membership snapshot, RNG draw counts, and the move trace.

One CM run on a small fixture produces tens to hundreds of records. The cumulative ~694K records across the four panels comes from many CM runs on many input graphs at many seeds; each individual run's record list is small. The byte-equal check is per record: the JS walker's record at position \(i\) must bit-match the canonical tracer's record at position \(i\), across every field. A single field mismatch is a fail; the harness reports which field, which record, which cell.

The record schema covers nine field types: INIT_LINEAGE for each seed-step component, MINCUT_POP for each pop, RECLUSTER_SIDE for each base-algo call (one per failing side), END_ROUND_DRAIN for each round boundary, EMIT_DONE for each survivor emission, WRITE_OUTPUT for each row of com.csv, WRITE_HISTORY for each parent row in history.log, plus per-Leiden-iteration probes LD_BEGIN / LD_END with membership snapshots, and per-pop singleton-count probes. Reading the field list gives a sense of how much state the harness has to track: the lineage assignment alone has 8 fields per component (component index, first node id, original cid, original size, sub-size, branch, parent cid, current cid).

The threshold value is recorded as a uint64 bit pattern (the IEEE 754 binary representation of the double) rather than a decimal string. This makes the check sensitive to last-bit rounding differences between the two log primitives (glibc and V8 fdlibm). Most of the time the bit patterns agree; on the ~0.09% of inputs where they differ, the byte-equal harness flags the cell, and the discrepancy is traced back to the log primitive. The TRACER_MODE swap aligns the log primitive on the canonical side with the JS port, removing the only systematic source of bit-level disagreement.

Three claims, layered

The byte-equal verification splits into three claims for clarity:

  1. JS visualizer == canonical tracer (TRACER_MODE swapped build). True across all 513 stress matrix cells. The "swapped build" replaces glibc std::log with the same V8 fdlibm port the JS walker uses, replaces libstdc++ MT19937 with the JS MT19937 family, and replaces std::unordered_set with std::set in the hot loops to match JS Map ordering. Under those swaps, the canonical C++ trace and the JS trace bit-match per pop.
  2. canonical tracer (CANONICAL_MODE build) == production canonical pipeline. True. The CANONICAL_MODE build leaves the original glibc + libstdc++ + std::unordered_set untouched; it adds instrumentation probes only. The two emit the same partition.
  3. JS visualizer == production canonical pipeline. Modulo the two structural primitive swaps in claim 1, true. The trajectory is identical; the bit-representation of the threshold value and the order of mincut RNG draws differ. End partitions match in 100% of stress cells empirically; bit-level identity is not asserted.

The chained verification of claims 1 + 2 implies the trajectory equality in claim 3, even without bit-level identity, because the two primitive swaps are localised to known sites and their effects are bounded. Anyone running the binary on the same input will get the same partition the walker produces, byte-equal up to the two known primitive families.

What the verification does not cover

The byte-equal check has scope limits worth naming. The check covers single-thread execution exclusively; multi-threaded CM runs (under --num-processors greater than 1) have non-deterministic cluster id assignment because worker threads pull from the FIFO concurrently. The partition itself is stable under multi-thread, but the row order of com.csv varies. The byte-equal harness fixes --num-processors 1 and does not assert anything about multi-thread behaviour.

The check also covers only the binary's stage 3 logic plus the seed step. The Python wrapper's stage 2 filter (drop clusters below \(B\) and tree clusters) and stage 4 filter (drop fragments below \(B\)) are not in the binary, so the byte-equal check does not test them. The JS walker also does not apply these filters, so the walker's "final" partition can include small fragments that the wrapper would drop. Comparing the walker's output to a wrapper run's output requires applying \(B = 11\) post-hoc to the walker's survivor list.

The check covers the four base-algo configurations in the stress matrix (Leiden-CPM at 0.0001, Leiden-CPM at 0.5, Leiden-Mod, and SBM-Flat-PP as input source). Louvain as a re-clusterer and Infomap as either input source or re-clusterer are not in today's stress matrix; the verification for those configurations is pending future cycles.

stage 10 · take-home

What this page covered.

CM is the heaviest of three connectivity post-procs in the same binary. It takes a clustering as input, walks each cluster through a mincut + threshold check, and on failure re-clusters each cut half with the base algorithm. The output is a partition where every cluster is well-connected under the threshold AND locally optimal under the base algorithm's quality function, modulo the size filter applied downstream.

Three forces shape every CM run. The threshold function determines which clusters are subjected to the modify-or-keep choice. The mincut produces the bipartition that exposes the cluster's bottleneck. The base algorithm re-clusters each cut half and decides what each new sub-cluster looks like. Changing any of the three changes the output.

Two practical observations from the gallery's stress matrix. The byte-equal verification covers four panels totalling 513 cells with ~694K records on the CM-specific path; zero mismatches mean the JS walker reproduces the canonical binary's behaviour bit for bit under matching seed. The two RNG streams (VieCut's mincut RNG, the base algorithm's RNG) are independent; the FP path has exactly one log primitive in the threshold check; the queue dynamics are FIFO and deterministic.

Cross-link directions: CC does the seed step only; WCC adds the threshold and the recursive cut; CM adds the base-algo re-cluster. Leiden CPM is the inner re-clusterer in the default deployed configuration. VieCut is the mincut backend. The technical companion at the link below traces every source-code reference for users porting CM to other languages or auditing the JS port against the canonical binary.

What the page does not cover

Scope limits worth naming for users coming to CM for the first time. The walker shows the binary's stage 3 only; the Python wrapper's stages 2 and 4 (size filter + tree filter + degree-band prune + post-CM filter) are visible in the lineage tree but not applied. Anyone running the canonical pipeline end-to-end will see a partition that has gone through the wrapper's filters as well.

The page does not cover the multi-threaded binary mode. Under --num-processors greater than 1, worker threads pull from the FIFO concurrently and cluster id labels become non-deterministic across runs. The walker pins to single-thread, which is also what the byte-equal verification requires. Anyone running the canonical pipeline on a large network should expect partition stability but label instability under multi-thread.

The page does not cover the prune branch's full degree-band pre-prune (only the singleton-trivial-cut variant lives in the binary). Anyone wanting Park 2024's stage 3 exactly should add a pre-pass that drops nodes below the threshold from each cluster's induced subgraph before mincut.

The page does not cover Infomap or Louvain as re-clusterers. The wrapper accepts Leiden CPM, Leiden Mod, and Louvain; the byte-equal verification today covers Leiden CPM (at two resolutions) and Leiden Mod. Louvain and Infomap are in the binary but not in the gallery's stress matrix; their behaviour with CM is described qualitatively in the chain-input section above.

A glossary for one page

Terms used throughout this page, with short definitions for quick reference:

Cluster. A set of nodes carrying the same partition label.

Induced subgraph. The subgraph spanned by a cluster's nodes; intra-cluster edges only, no cross-cluster edges.

Mincut. The minimum number of edges whose removal disconnects a graph (here, the cluster's induced subgraph).

Threshold function. A function \(f(n)\) that maps cluster size to a minimum required mincut. The cluster passes iff its mincut strictly exceeds \(f(n)\).

Well-connected. A cluster whose mincut clears the threshold for its size.

Re-cluster step. Run the base community-detection algorithm on a cluster's induced subgraph; replace the cluster with whatever communities the base algorithm returns.

Lineage tree. A directed acyclic graph recording parent-child relationships between input clusters and their CM-modified descendants.

Cluster fate. A label per input cluster summarising what CM did to it: extant (unchanged), reduced (one smaller child), split (multiple children), or degraded (all children dropped by post-CM filter).

Round. One full pass through to_be_mincut, draining it to either the survivor list or to to_be_clustered for the next round.

Stage 3. Park 2024's name for the CM loop itself (mincut + threshold check + re-cluster). The binary implements stage 3; the Python wrapper implements stages 1, 2, 4.

FIFO. First-in first-out queue discipline. Both to_be_mincut and to_be_clustered are FIFO; the order clusters enter is the order they get processed.
