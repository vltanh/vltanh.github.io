CM

connectivity modifier · Park 2024

The heaviest of three connectivity post-procs. WCC's cut, plus a re-run of the base community-detection algorithm on each cut half before the recursion advances.

Draft. Under-construction trace for the CM post-processor on the shared 32-node fixture. The page keeps under-construction status until reviewed; read the walker as an explanatory trace of cut, recluster, and repeat.

CC drops cross-cluster edges and splits each cluster into its connected pieces. WCC adds a threshold: a cluster has to clear a mincut bound or it gets cut and recursed. CM is the heaviest: WCC plus a Leiden recluster on each cut half before the recursion advances.

The modifier in the name is literal. CC and WCC are filters: the output labels descend from the input labels. CM rewrites them. Post-cut halves are not bound to the input partition; if the base algorithm returns four communities on an 80-node induced subgraph, CM feeds those four into the next round.

The threshold uses the same parser as WCC:

\( f(n) = C \log_x(n) \quad \text{or} \quad f(n) = C\,n^x \)

In words: a cluster of \(n\) nodes passes iff its minimum edge cut is strictly larger than \(f(n)\). Two interesting properties: the threshold is monotone in \(n\), so as a cluster shrinks under repeated cuts the bar drops with it, which is why the recursion terminates; and the threshold depends only on size, not on cluster density.

Park 2024 (PLOS Complex Systems 1(3):e0000009) gives \( f(n) = \log_{10}(n) \) as the primary criterion. The pipeline wrapper ships \(0.2 \cdot n^{0.5}\) instead. The two cross at \(n = 100\); below that, the log criterion is stricter.

The shipped loop seeds itself with CC components, runs the WCC mincut-threshold test, and on failure runs Leiden or Louvain inside each non-singleton cut side before staging children for the next round. On the shared fixture under \(\log_{10}\), CM follows WCC's A-peeling path because Leiden CPM returns one community on each residual side; when the base splits a side into multiple communities, CM diverges from WCC immediately.

CM changes labels and lineage. Park 2024 splits the full pipeline into initial base clustering, a size filter, the CM loop, and a final size filter; this page's walker covers the binary loop only. Wrapper-only pre/post size filters can remove survivors later, and multi-threaded runs can vary row order even when the partition is stable. The binary writes a parent \(\rightarrow\) child tree, and the extant, reduced, split, and degraded labels are computed downstream from that tree.

why Leiden as inner re-clusterer, not Louvain

Leiden's refinement phase gives stronger connectivity than Louvain, so the subsequent component sweep usually has less repair work. Louvain can return disconnected labels, which the sweep may fragment. Both are supported in the binary; src/cm/pipeline.sh has no base-algorithm default and requires --base-algo. This page opens on Leiden CPM as a teaching choice.

stage 0 · input

The planted partition.

32 nodes, 52 edges, four planted communities plus two outliers. Cluster A is a K5 core with seven periphery nodes hanging off it by single edges. Cluster B is two K4's joined by one bridge edge. Cluster C is two disjoint 3-cycles sharing one label. Cluster D is two 2-cliques. Nodes 30 and 31 sit unclustered. The same fixture is used on the CC and WCC pages.

stage 1 · strip + connected components

The seed step, same as CC.

CM's first action drops every cross-cluster edge from the residual graph, then runs breadth-first search on each cluster's surviving subgraph in node-id order. Disconnected input clusters fragment here, before any mincut runs. The fixture's cluster C is the case: its two 3-cycles share one label but live in separate components, so the seed step splits them into C1 and C2.

Why split first, then run mincut? Mincut is undefined on a disconnected graph (the cut value is trivially 0). BFS once per cluster, hand the cut loop only connected pieces.

stage 2 · lineage id assignment

Keep the original id, or mint a fresh one?

CM tracks which output cluster descended from which input cluster, because the cluster-fate classification reads the parent → child tree. The rule is one comparison per component:

\( \text{if } |\text{component}| = |\text{original cluster}| \text{ then keep the original id, else mint a fresh id with parent } = \text{original} \)

In words: a component covering its entire input cluster keeps the original id; a strict subset gets a fresh id and a parent link. The first fragment of each input cluster also records the row "(parent = root, child = original id)" exactly once. Two interesting properties: the root row records every input cluster that ever fragmented, so the cluster-fate analyzer finds the split inputs by scanning a single row; and ids are never re-used, so the tree is always acyclic.

stage 3 · the threshold function

What \(f(n)\) says and why.

The well-connectedness test is:

\( \text{threshold} = \text{pre\_log} \cdot \log(n) \)
\( \text{is\_close} = | \text{threshold} - \text{cut} | \leq 10^{-9} \)
\( \text{well\_connected} = (\text{not is\_close}) \wedge (\text{threshold} < \text{cut}) \)

In words: a cluster is well-connected when its cut is strictly above the threshold and not numerically tied to it. The constant \(\text{pre\_log} = C / \log(x)\) is computed once at startup, so per-cluster work is one log call and one multiply. Two interesting properties: a smaller cluster always faces a smaller threshold (log is monotone), so a cluster that fails the bar once cannot recover by surviving a cut that just shrunk it; and the comparison is strict, so a cluster sitting exactly at \(f(n)\) within tolerance fails, not passes.

stage 4 · mincut as a primitive

What VieCut returns per pop.

VieCut returns the minimum cut size (an edge count) plus the bipartition of the cluster into two sides. Among all bipartitions achieving the minimum, VieCut picks the most balanced one. Balance keeps recursion depth bounded: without it, a "trivial cut" peeling one node at a time would produce recursion depth \(n\) instead of \(\log n\).

stage 5 · verdict and side filter

Pass means survivor; fail means re-cluster each side.

The verdict reads the threshold check. Pass: the cluster is well-connected, push it to the survivor list, no further work. Fail: cut along the bipartition, and hand each side of size \(>1\) to the base algorithm. Sides of size 1 are filtered by the strict-greater-than-one gate and drop out; that is what bounds singletons to one extra round instead of an unbounded loop.

On cluster A under \(\log_{10}\): cut 1, threshold \(\log_{10}(12) \approx 1.079\), so \(1 > 1.079\) is false, fail. VieCut returns a balanced cut peeling one periphery node. The 1-node side is filtered. The 11-node side goes through the re-cluster step.

stage 6 · Leiden replay on the failing side

What makes CM different from WCC.

This is the step that separates CM from WCC. After a failing cut, CM does not push the two cut halves back directly. For each side of size larger than one, CM builds the induced subgraph of that side and runs Leiden CPM on it for two iterations. Whatever communities Leiden returns become the new clusters; each one is pushed back with the failing cluster's id as parent.

One failing cluster can therefore produce more than two children. If Leiden finds three sub-communities in the 11-node side, all three are pushed back, and the lineage tree branches accordingly. On the 32-node fixture at \(r = 0.0001\), Leiden returns one community on every side, so the chain is linear; at \(r = 0.5\), Leiden returns multiple communities and the chain branches.

Two interesting properties: the re-cluster step is run on the induced subgraph of the side alone, not the full cluster, so Leiden's view is local; and Leiden's RNG is re-seeded to 0 at every call, so two re-cluster runs on the same induced subgraph produce the same partition regardless of where they sit in the pop sequence.

why this step is the heaviest in the CM family

CC does the seed step only. WCC adds the threshold check and the recursive cut. CM adds the Leiden replay. The cost of one re-cluster call is \(O(n + m)\) per Leiden iteration with two iterations per call. On large clusters this dominates the per-pop cost.

stage 7 · round drain

End of round: every pending entry gets a fresh id.

CM runs in rounds. One round drains the mincut queue entirely, producing either survivors or re-cluster outputs. The re-cluster outputs land in a pending queue for the next round. When the round ends, every pending entry gets a fresh id from a counter, records its parent link in the lineage tree, and migrates back to the mincut queue. The round counter ticks.

Termination: a round produces no work for the next round. Equivalent statement: every cluster in the most recent round either survived or got cut into singletons that the size-greater-than-one gate filtered.

stage 8 · the walker

Cut, threshold check, Leiden replay, round by round.

The walker scrubs through every pop in order. Each pop has a size, a cut, a threshold, a verdict. Edge-of-round events (drains and id assignments) surface under the per-round granularity toggle. Changing the base algorithm, resolution, criterion, or seed re-runs the kernel live.

Step 1. Pop the next current-round cluster from to_be_mincut and build the induced edge set on that node set. Step 2. Ask VieCut for the minimum edge cut and a balanced bipartition. Step 3. Compare the cut to \(f(n)\). A pass appends the cluster to survivors and creates no children.

Step 4. A fail treats the two cut sides as repair material. Direct singleton sides are skipped. Every other side is remapped to a local induced subgraph and sent through the selected base algorithm. Step 5. CM removes inter-community edges from the base output, runs connected components, and stages each returned component in to_be_clustered with the failing cluster as parent.

Step 6. At round drain, all staged children receive fresh ids, parent-child rows are written, and the children migrate back to to_be_mincut. That is the difference from WCC: WCC's failing branch pushes the cut pieces themselves; CM lets the base objective rewrite each non-singleton cut side before the next mincut round.

stage 9 · lineage tree

Cluster history: parent → children across rounds.

Each input cluster traces a tree as CM splits and re-clusters it. Roots are the initial connected components. Each internal edge is one cut and one Leiden replay. Leaves are survivors (green), in-flight clusters (amber), or dropped singletons (grey). The cluster-fate label is reconstructable from this tree alone, which is why the binary writes it to disk.

On the 32-node fixture under \(\log_{10}\): A's lineage is the linear chain \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\) (four ids, three rounds, leaf at the 9-node residual). stage 10 · worked example

Cluster A's three rounds, mincut by mincut.

Cluster A is the only cluster that fails the \(\log_{10}\) threshold on this fixture. 12 nodes, K5 core, seven periphery nodes each attached by a single edge. Its trajectory through the loop covers every operation CM performs.

Round 0. Pop A at \(n=12\): cut \(1\), threshold \(1.079\), verdict fail. VieCut peels one periphery node, the size-1 side is filtered, and Leiden CPM at \(r=0.0001\) runs on the 11-node side. At this low resolution CPM returns one community of 11, which is staged for the next round with A as parent.

Round 1. Pop id 6 at \(n=11\): cut \(1\), threshold \(\log_{10}(11) \approx 1.041\), verdict fail. The same shape peels one pendant, and the 10-node side goes through Leiden replay. Round 2. Pop id 7 at \(n=10\): cut \(1\), threshold \(\log_{10}(10) = 1.000\). The difference is inside the \(10^{-9}\) guard, so is_close is true and the strict comparison fails.

Round 3. Pop id 8 at \(n=9\): cut \(1\), threshold \(\log_{10}(9) \approx 0.954\), verdict pass. The 9-node residual survives. The lineage is \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\), and the final survivor list is A residual, B, C1, C2, D. Three peeled pendants vanish through the size-1 filter.

The chain has length 4 because A's threshold has to drop below 1 before the cut of 1 stops counting as a failure. The crossover is at \(n = 9\), where \(\log_{10}\) finally falls below 1. Two interesting properties: the chain length depends only on the threshold function and the starting cluster size (not on structure beyond the mincut value); and the Leiden replay plays a passive role at \(r = 0.0001\) because it keeps returning one community, so CM is effectively running WCC with a Leiden no-op in the middle.

CC + WCC cross-link

If A's trajectory feels familiar from WCC, that is not a coincidence: WCC and CM produce the same partition on A here, because Leiden CPM at r=0.0001 returns one community on every side, so the re-cluster step is a no-op. The two diverge when the base algorithm splits a side into multiple communities.

stage 11 · cluster fate dictionary

Four labels Park 2024 §4.2 reads from the lineage tree.

Extant. One child, same id as parent. The cluster passed every threshold check and appears in the output unchanged. On this fixture under \(\log_{10}\), B, C1, C2, and D are extant. Reduced. One child, smaller node set. A follows \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\) and ends at 9 nodes, down from 12.

Split. Two or more children. This can happen because the base algorithm returned multiple communities on a cut half, or because the seed step started with multiple components for one input id; C on this fixture is the seed-step split. Degraded. Every leaf descendant ended up below the post-CM size filter \(B\), default 11, so the cluster is effectively erased. This label lives in the Python wrapper and is not surfaced by the walker.

The four labels are exhaustive and disjoint per input cluster. Park 2024 §4.4 reports: under Leiden-CPM at low resolution, "split" and "reduced" dominate; under IKC at k=10, most clusters are "extant"; Leiden-Mod sits in between.

stage 12 · edge cases

What CM does at the corners.

Leiden returns the same partition

The base algorithm is a fixed point on its own quality function, so the re-cluster can return one community spanning the whole input side. CM pushes that single community back; next round it gets mincut again. Termination relies on the threshold dropping as the cluster shrinks.

cluster disintegrates into singletons

A re-cluster on an n-node side can return n singletons. The binary pushes them all to the next-round queue. Next round each singleton fails the threshold; the re-cluster on a size-1 side is filtered by the size-greater-than-one gate and the singleton vanishes. One extra round, not an infinite loop.

threshold equals cut exactly

The strict comparison with a \(10^{-9}\) tolerance sends ties to fail, so a cluster sitting exactly at \(f(n)\) gets re-cut. The asymmetry is by design: a post-proc that flags under-cohesive clusters treats equality as the conservative side.

tree-shaped cluster

A tree has mincut 1 by construction, so every tree cluster fails the threshold under \(\log_{10}\) for any \(n \geq 2\). The recursion peels one edge at a time, dissolving the cluster down to singletons. The Python wrapper filters tree clusters before stage 3 to avoid spending compute on them.

multi-threading: ids vary, partition stable

Under multi-thread mode, worker threads pull from the FIFO concurrently and fresh-id assignment depends on which thread pops first. The partition itself is stable; only labels and row order vary. The verification harness pins to single-thread.

VieCut RNG state drift across pops

VieCut is seeded once at startup and not re-seeded per call (the intended per-call re-seed is commented out in the source). Two pops on identical induced subgraphs at different points in the run can produce different bipartitions when ties exist. The JS port mirrors the drift exactly.

criterion = "0" disables CM

Setting the criterion to a constant zero makes every connected cluster pass. CM degenerates to the seed step alone; the output equals CC's output.
