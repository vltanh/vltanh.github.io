community detection · post-proc · connectivity modifier

CM

connectivity modifier · Park 2024

The heaviest of three connectivity post-procs. WCC's cut, plus a re-run of the base community-detection algorithm on each cut half before the recursion advances.

CC drops cross-cluster edges and splits each cluster into its connected pieces. WCC adds a threshold: a cluster has to clear a mincut bound or it gets cut and recursed. CM is the heaviest: WCC plus a Leiden recluster on each cut half before the recursion advances.

The word in "connectivity modifier" carries weight. CC and WCC are filters: the output labels are descendants of the input labels. CM modifies: post-cut halves are not stuck with the input partition. If the base algorithm sees an 80-node induced subgraph and decides it is really four communities, CM accepts that and feeds the four into the next round.

The threshold uses the same parser as WCC:

\( f(n) = C \log_x(n) \quad \text{or} \quad f(n) = C\,n^x \)

In plain English: a cluster of \(n\) nodes passes iff its minimum edge cut is strictly larger than \(f(n)\). Two interesting properties: the threshold is monotone in \(n\), so as a cluster shrinks under repeated cuts the bar drops with it, which is why the recursion terminates; and the threshold is independent of cluster density, only of size.

Park 2024 (PLOS Complex Systems 1(3):e0000009) gives \( f(n) = \log_{10}(n) \) as the primary criterion. The pipeline wrapper ships \(0.2 \cdot n^{0.5}\) instead. The two cross at \(n = 100\); below that, the log criterion is stricter.

pipeline shape Park 2024 splits the procedure into four stages: initial base clustering, a size filter, the CM loop (this page's walker), and a final size filter. The walker covers stage 3. Stages 2 and 4 live in the Python orchestration around the binary.
re-cluster step CM runs the base algorithm on the induced subgraph of one cut half, then again on the other half. Each call gets a fresh seed.
cluster fate Park 2024 §4.2 classifies every input cluster as extant, reduced, split, or degraded. The binary writes a tree of parent → children; the four labels are computed downstream from that tree.
why Leiden as inner re-clusterer, not Louvain

Leiden's refinement phase guarantees every output community is internally connected, so the subsequent connectivity sweep on the re-cluster output usually splits nothing further. Louvain has no such guarantee, so the connected-components sweep after a Louvain re-cluster can fragment communities further and pad the work queue. Both are supported in the binary; the pipeline defaults to Leiden CPM.

stage 0 · input

The planted partition.

32 nodes, 52 edges, four planted communities plus two outliers. Cluster A is a K5 core with seven periphery nodes hanging off it by single edges. Cluster B is two K4's joined by one bridge edge. Cluster C is two disjoint 3-cycles sharing one label. Cluster D is two 2-cliques. Nodes 30 and 31 sit unclustered. The same fixture is used on the CC and WCC pages.

stage 1 · strip + connected components

The seed step, same as CC.

CM's first action drops every cross-cluster edge from the residual graph, then runs breadth-first search on each cluster's surviving subgraph in node-id order. Disconnected input clusters fragment here, before any mincut runs. The fixture's cluster C is the case: its two 3-cycles share one label but live in separate components, so the seed step splits them into C1 and C2.

Why split first, then run mincut? Mincut is undefined on a disconnected graph (the cut value is trivially 0). BFS once per cluster, hand the cut loop only connected pieces.

stage 2 · lineage id assignment

Keep the original id, or mint a fresh one?

CM tracks which output cluster descended from which input cluster, because the cluster-fate classification reads the parent → child tree. The rule is one comparison per component:

\( \text{if } |\text{component}| = |\text{original cluster}| \text{ then keep the original id, else mint a fresh id with parent } = \text{original} \)

In plain English: if a component covers its entire input cluster, the original id stands. If the component is a strict subset, CM mints a fresh id and records the parent link. The first fragment of each input cluster also records the row "(parent = root, child = original id)" exactly once. Two interesting properties: the root row records every input cluster that ever fragmented, so the cluster-fate analyzer finds the split inputs by scanning a single row; and ids are never re-used, so the tree is always acyclic.

stage 3 · the threshold function

What \(f(n)\) says and why.

The well-connectedness test is:

\( \text{threshold} = \text{pre\_log} \cdot \log(n) \)
\( \text{is\_close} = | \text{threshold} - \text{cut} | \leq 10^{-9} \)
\( \text{well\_connected} = (\text{not is\_close}) \wedge (\text{threshold} < \text{cut}) \)

In plain English: a cluster is well-connected if its cut is strictly above the threshold AND the cut is not numerically tied with the threshold. The constant \(\text{pre\_log} = C / \log(x)\) is computed once at startup, so per-cluster work is one log call and one multiply. Two interesting properties: a smaller cluster always faces a smaller threshold (log is monotone), so a cluster that fails the bar once cannot recover by surviving a cut that just shrunk it; and the comparison sits strictly above the threshold, so a cluster sitting exactly at \(f(n)\) within tolerance fails, not passes.

stage 4 · mincut as a primitive

What VieCut returns per pop.

VieCut returns the minimum cut size (an edge count) plus the bipartition of the cluster into two sides. Among all bipartitions achieving the minimum, VieCut picks the most balanced one. Balance keeps recursion depth bounded: without it, a "trivial cut" peeling one node at a time would produce recursion depth \(n\) instead of \(\log n\).

stage 5 · verdict and side filter

Pass means survivor; fail means re-cluster each side.

The verdict reads the threshold check. Pass: the cluster is well-connected, push it to the survivor list, no further work. Fail: the bipartition is the place to cut, and CM hands each side of size \(>1\) to the base algorithm. Sides of size 1 are filtered by the strict-greater-than-one gate and vanish; this is what makes singletons die after one extra round rather than loop forever.

On cluster A under \(\log_{10}\): cut 1, threshold \(\log_{10}(12) \approx 1.079\), so \(1 > 1.079\) is false, fail. VieCut returns a balanced cut peeling one periphery node. The 1-node side is filtered. The 11-node side goes through the re-cluster step.

stage 6 · Leiden replay on the failing side

What makes CM different from WCC.

This is the step that lifts CM above WCC. After a failing cut, CM does not push the two cut halves directly back. Instead, for each side of size larger than one, CM builds the induced subgraph of that side alone and runs Leiden CPM on it for two iterations. Whatever communities Leiden returns become the new clusters; each one gets pushed back with the failing cluster's id as parent.

The implication: a single failing cluster can spawn many children, not just two. If Leiden finds three sub-communities in the 11-node side, all three get pushed back. The lineage tree branches accordingly. On the 32-node fixture under \(r = 0.0001\), Leiden returns one community on every side it sees, so the chain is linear; on \(r = 0.5\), Leiden returns multiple communities and the chain branches.

Two interesting properties: the re-cluster step is run on the induced subgraph of the side alone, not the full cluster, so Leiden's view is local; and Leiden's RNG is re-seeded to 0 at every call, so two re-cluster runs on the same induced subgraph produce the same partition regardless of where they sit in the pop sequence.

why this step is the heaviest in the CM family

CC does the seed step only. WCC adds the threshold check and the recursive cut. CM adds the Leiden replay. The cost of one re-cluster call is \(O(n + m)\) per Leiden iteration with two iterations per call. On large clusters this dominates the per-pop cost.

stage 7 · round drain

End of round: every pending entry gets a fresh id.

CM runs in rounds. One round drains the mincut queue entirely, producing either survivors or re-cluster outputs. The re-cluster outputs land in a pending queue for the next round. When the round ends, every pending entry gets a fresh id from a counter, records its parent link in the lineage tree, and migrates back to the mincut queue. The round counter ticks.

Termination: a round produces no work for the next round. Equivalent statement: every cluster in the most recent round either survived or got cut into singletons that the size-greater-than-one gate filtered.

stage 9 · lineage tree

Cluster history: parent → children across rounds.

Each input cluster traces a tree as CM splits and re-clusters it. Roots are the initial connected components. Each internal edge is one cut + Leiden replay. Leaves are survivors (green), in-flight clusters (amber), or dropped singletons (grey). The cluster-fate label is reconstructable from this tree alone, which is why the binary writes it to disk.

On the 32-node fixture under \(\log_{10}\): A's lineage is the linear chain \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\) (four ids, three rounds, leaf at the 9-node residual). Under the wrapper's sqrt default the tree is empty (no input cluster fragmented). Under \(2 \cdot \log_{10}\) B would also fail and produce a separate chain.

stage 10 · worked example

Cluster A's three rounds, mincut by mincut.

Cluster A is the only cluster that fails the \(\log_{10}\) threshold on this fixture. 12 nodes, K5 core, four periphery pendants each attached by a single edge. Walking its trajectory exposes every moving part of the loop.

round 0 · pop A n=12, cut=1, threshold=1.079. verdict: fail VieCut peels one periphery node. The 1-node side is filtered.
round 0 · Leiden replay Leiden CPM r=0.0001 runs on the 11-node side. output: one community of 11 At low resolution, CPM prefers one community. It pushes to the next-round queue with A as parent.
round 1 · pop id 6 n=11, cut=1, threshold \(\log_{10}(11) \approx 1.041\). verdict: fail Same shape: peel one pendant, recluster the 10-node side.
round 2 · pop id 7 n=10, cut=1, threshold \(\log_{10}(10) = 1.000\). verdict: fail (tie) \(1.000 - 1\) is within the \(10^{-9}\) guard, so is_close is true: fail.
round 3 · pop id 8 n=9, cut=1, threshold \(\log_{10}(9) \approx 0.954\). verdict: pass \(1 > 0.954\). The 9-node residual survives. Lineage: \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\).
final Output: 5 survivors. A residual, B, C1, C2, D Three peeled pendants vanish (size-1 sides filtered).

The chain has length 4 because A's threshold has to drop below 1 before the cut of 1 stops counting as a failure. The crossover is at \(n = 9\), where \(\log_{10}\) finally falls below 1. Two interesting properties: the chain length depends only on the threshold function and the starting cluster size (not on structure beyond the mincut value); and the Leiden replay plays a passive role at \(r = 0.0001\) because it keeps returning one community, so CM is effectively running WCC with a Leiden no-op in the middle.

CC + WCC cross-link

If A's trajectory feels familiar from WCC, that is not a coincidence: WCC and CM produce the same partition on A here, because Leiden CPM at r=0.0001 returns one community on every side, so the re-cluster step is a no-op. The two diverge when the base algorithm splits a side into multiple communities.

stage 11 · cluster fate dictionary

Four labels Park 2024 §4.2 reads from the lineage tree.

extant

One child, same id as parent. The cluster passed every threshold check; it shows up in the output unchanged. On this fixture under \(\log_{10}\): B, C1, C2, D.

reduced

One child, smaller node set. A on this fixture: \(0 \rightarrow 6 \rightarrow 7 \rightarrow 8\) ends at 9 nodes, down from 12.

split

Two or more children. The base algorithm returned multiple communities on at least one cut half, or the seed step started with multiple components for one input id. C on this fixture is the seed-step split.

degraded

Every leaf descendant ended up below the post-CM size filter \(B\) (default 11). The cluster is effectively erased. Lives in the Python wrapper; not surfaced by the walker.

The four labels are exhaustive and disjoint per input cluster. Park 2024 §4.4 reports: under Leiden-CPM at low resolution, "split" + "reduced" dominate; under IKC at k=10, most clusters are "extant"; Leiden-Mod sits in between.

stage 12 · edge cases

What CM does at the corners.

Leiden returns the same partition

The base algorithm is a fixed point on its own quality function, so the re-cluster can return one community spanning the whole input side. CM pushes that single community back; next round it gets mincut again. Termination relies on the threshold dropping as the cluster shrinks.

cluster disintegrates into singletons

A re-cluster on an n-node side can return n singletons. The binary pushes them all to the next-round queue. Next round each singleton fails the threshold; the re-cluster on a size-1 side is filtered by the size-greater-than-one gate and the singleton vanishes. One extra round, not an infinite loop.

threshold equals cut exactly

The strict comparison with a \(10^{-9}\) tolerance sends ties to fail. A cluster sitting exactly at \(f(n)\) gets re-cut. The bias is intentional: a post-proc looking for under-cohesive clusters treats equality as "fail".

tree-shaped cluster

A tree has mincut 1 by construction, so every tree cluster fails the threshold under \(\log_{10}\) for any \(n \geq 2\). The recursion peels one edge at a time and the cluster effectively melts. The Python wrapper filters tree clusters before stage 3 to avoid spending compute on them.

multi-threading: ids vary, partition stable

Under multi-thread mode, worker threads pull from the FIFO concurrently and fresh-id assignment depends on which thread pops first. The partition itself is stable; only labels and row order vary. The verification harness pins to single-thread.

VieCut RNG state drift across pops

VieCut is seeded once at startup and not re-seeded per call (the intended per-call re-seed is commented out in the source). Two pops on identical induced subgraphs at different points in the run can produce different bipartitions when ties exist. The JS port mirrors the drift exactly.

criterion = "0" disables CM

Setting the criterion to a constant zero makes every connected cluster pass. CM degenerates to the seed step alone; the output equals CC's output.
