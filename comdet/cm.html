CM

connectivity modifier · Park 2024

The heaviest of the three connectivity post-procs. WCC's cut + a re-run of the base clustering algorithm on each cut half before the recursion advances. Iterates to a fixed point where every output cluster is both well-connected and locally optimal under the base objective.

Walker pending. The per-stage walker for CM waits on the Phase 4c port (mincut + Leiden kernel both have to land first). Today the page surfaces the input fixture and the planned stage list. The technical companion at docs/algorithms/cm.md covers source pointers, fate vocabulary, and the binary's flag surface.

CM does what WCC does (cut a cluster whose mincut falls below the threshold), then re-runs the base community-detection algorithm (Leiden CPM, Leiden Mod, Louvain, Infomap) on the induced subgraph of each cut half. The output of that re-run replaces the cut halves; every produced sub-cluster goes back through the threshold check. The loop repeats until no cluster fails.

This buys two things WCC does not. First, the post-cut halves are not stuck with the input partition's labels: if WCC cut a 200-node cluster into halves of 70 and 130, CM lets the base algorithm find smaller real communities inside each. Second, an output cluster is locally optimal under both the connectivity threshold and the base algorithm's quality function, not one or the other.

The threshold uses the same parser as WCC: \( f(n) = C \log_x(n) \) or \( f(n) = C\,n^x \). Park 2024 (PLOS Complex Systems 1(3):e0000009) recommends \( f(n) = \log_{10}(n) \). Our pipeline ships 0.2n^0.5 instead, a sqrt criterion that diverges from the paper's default.

cluster fate Park 2024 §4.2 classifies every input cluster as one of four fates: extant (unchanged), reduced (smaller but still one cluster), split (two or more sub-clusters), degraded (every leaf descendant ended up below the size filter B, default 11). The binary writes a history.log tree of parent → children so the fate is reconstructable per input cluster.
re-cluster step CM does not re-run the base algorithm globally. It runs the base algorithm on the induced subgraph of one cut half, then again on the other half. Each call gets a fresh `seed = 0` (the base algo's RNG is re-seeded per call); only VieCut's mincut RNG carries state across rounds.
pre-prune Park 2024's Stage 3 specifies an iterative pre-prune that strips low-degree nodes (degree ≤ f(n) in the cluster's induced subgraph) before the cut. The binary exposes this via --prune; the src/cm/pipeline.sh wrapper does not pass the flag, so today's CM runs without pre-prune.
when CM moves the needle · Park 2024 §4.4

Heaviest gain comes on Leiden-CPM at small resolution (\( r \in [0.0001, 0.001] \)) where the base algorithm over-merges; CM peels apart real sub-communities that CPM left bundled. Lightest gain (or even slight loss) on already-conservative algorithms like IKC at k=10, where most clusters come through unchanged. Leiden-Mod sits in between, with a meaningful fraction of its clusters split. The paper's empirical verdict: CM is most useful as a sharpener for over-merging base algorithms, less so as a corrector for over-splitting ones.
