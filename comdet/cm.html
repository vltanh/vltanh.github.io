CM

connectivity modifier · Park 2024

The heaviest of the three connectivity post-procs. WCC's cut + a re-run of the base clustering algorithm on each cut half before the recursion advances. Iterates to a fixed point where every output cluster is both well-connected and locally optimal under the base objective.

CM does what WCC does (cut a cluster whose mincut falls below the threshold), then re-runs the base community-detection algorithm (Leiden CPM, Leiden Mod, Louvain, Infomap) on the induced subgraph of each cut half. The output of that re-run replaces the cut halves; every produced sub-cluster goes back through the threshold check. The loop repeats until no cluster fails.

This buys two things WCC does not. First, the post-cut halves are not stuck with the input partition's labels: if WCC cut a 200-node cluster into halves of 70 and 130, CM lets the base algorithm find smaller real communities inside each. Second, an output cluster is locally optimal under both the connectivity threshold and the base algorithm's quality function, not one or the other.

The threshold uses the same parser as WCC: \( f(n) = C \log_x(n) \) or \( f(n) = C\,n^x \). Park 2024 (PLOS Complex Systems 1(3):e0000009) recommends \( f(n) = \log_{10}(n) \). The pipeline wrapper ships 0.2n^0.5 instead, a sqrt criterion that diverges from the paper's default.

pipeline shape Park 2024 splits the procedure into four stages: (1) initial base clustering produces the input partition; (2) a size filter drops clusters below B (default 11) plus tree-shaped clusters; (3) the CM loop runs per cluster, with each round doing mincut, threshold check, and base-method recluster of any side > 1; (4) a final size filter drops sub-clusters that ended up below B. The walker below covers stage 3; stages 2 and 4 live in cm_pipeline around the binary.
cluster fate Park 2024 §4.2 classifies every input cluster as one of four fates: extant (unchanged), reduced (smaller but still one cluster), split (two or more sub-clusters), degraded (every leaf descendant ended up below the size filter B). The binary writes a history.log tree of parent → children so the fate is reconstructable per input cluster.
re-cluster step CM does not re-run the base algorithm globally. It runs the base algorithm on the induced subgraph of one cut half, then again on the other half. Each call gets a fresh seed = 0 (the base algo's RNG is re-seeded per call); only VieCut's mincut RNG carries state across rounds.
pre-prune Park 2024's Stage 3 specifies an iterative pre-prune that strips low-degree nodes (degree ≤ f(n) in the cluster's induced subgraph) before the cut. The binary exposes this via --prune; the src/cm/pipeline.sh wrapper does not pass the flag, so today's CM runs without pre-prune.
when CM moves the needle · Park 2024 §4.4

Heaviest gain comes on Leiden-CPM at small resolution (\( r \in [0.0001, 0.001] \)) where the base algorithm over-merges; CM peels apart real sub-communities that CPM left bundled. Lightest gain (or even slight loss) on already-conservative algorithms like IKC at k=10, where most clusters come through unchanged. Leiden-Mod sits in between, with a meaningful fraction of its clusters split. The paper's empirical reading: CM acts as a sharpener for over-merging base algorithms; less so as a corrector for over-splitting ones.

stage 3 · edge cases

What CM does at the corners.

leiden returns the same partition

The base algorithm is a fixed point on its own quality function, so a re-cluster can return one community spanning the whole input side. CM pushes that single community back into to_be_clustered; next round it will be mincut again. CM has no explicit guard against this, so a pathological input could loop. In practice Leiden CPM at low resolution converges, and the WCC threshold eventually accepts a sufficiently large component as well-connected.

cluster disintegrates into singletons

A re-cluster on an n-node side can return n singleton communities. Singletons of size 1 still get pushed into to_be_clustered, then the next-round mincut on a size-1 cluster is trivial (cut = 0, threshold > 0, well-connected = false), so they re-enter forever. The pipeline avoids this by using a post-filter step (size > B = 11 by default) at the end, not in the kernel itself. That filter is Park 2024's stage 4.

threshold equals cut exactly

CM uses the same epsilon-close test as WCC: |threshold - cut| ≤ 1e-9 resolves to not well-connected (push back). A cluster sitting exactly at the threshold gets re-cut and re-clustered. Equality is fragile; the strict threshold < cut after epsilon means "push back" is the safer call.
