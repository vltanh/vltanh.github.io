WCC

well-connected components · Park 2025 / Vu-Le 2026, threshold per Park 2024

A step up from CC. Each cluster has to clear a mincut threshold or it gets cut + recursed. Catches the case where a cluster is connected but only by a thin edge bridge: the kind of cluster that passes CC and still looks suspect to anyone who eyeballs it.

CC only asks whether a cluster is connected. That misses the case where a cluster is connected but only just: two large dense halves linked by a single bridge edge are formally connected, yet anyone eyeballing the graph would call them two communities. The cluster's mincut is 1, and 1 is suspiciously small for a cluster of any meaningful size.

WCC turns "is the cluster connected" into "is the cluster well-connected". The test replaces the binary connectedness check with a sliding threshold that scales with cluster size. A cluster passes iff its minimum edge cut strictly exceeds a size-dependent bound \(f(n)\), where \(n\) is the cluster's node count:

\[ \text{mincut}(C) > f(|C|) \]

In plain terms: the smallest number of edges that splits the cluster into two pieces must outpace some growth curve in the cluster's size. Two interesting properties: the threshold uses the cluster's size, not the graph's size, so a cluster's verdict does not depend on what other clusters look like; and the inequality is strict, so a cluster whose mincut exactly equals the threshold fails (treated the same as a clean miss).

The shipped default in the constrained-clustering binary picks \(f(n) = \log_{10}(n)\) following Park 2024. Other choices the binary accepts include \(C \log_x(n)\) for any base, \(C n^x\) for any exponent, and a piecewise schedule with constant cuts in three size bands and a square-root tail. The threshold stage below walks all four families.

If a cluster passes, leave it. If not, run the minimum cut, remove those edges, and recurse on each side. The recursion terminates because every cut strictly shrinks the cluster, and a cluster of one node short-circuits out.

mincut the smallest edge set whose removal disconnects the cluster. Computed exactly by VieCut's cactus algorithm (Henzinger, Noe, Schulz, Strash 2018) in near-linear time per cluster, so the post-proc stays cheap even on graphs with thousands of clusters.
balanced cut when several edge sets share the minimum cut value, the binary picks the most balanced of those minimum cuts. Each recursive half then carries roughly half the cluster, so the recursion depth stays shallow. Without that tie-break, the cut could peel one node at a time and stall.
threshold tie-handling the comparison is strict, with a small numerical tolerance: cuts that match the threshold to within \(10^{-9}\) are treated as failures. Cluster sizes where \(\log_{10}(n)\) equals an integer (\(n=10, 100, 1000\)) hit this case exactly when the cut is 1, 2, 3 respectively.
why WCC over CC · Vu-Le 2026

On the flat + nested stochastic block models tested in Vu-Le 2026 (every variant: degree-corrected, non-degree-corrected, planted-partition, plus PySBM), WCC's gain over the unprocessed clustering is uniformly larger than CC's. CC catches the disconnected-cluster case; WCC also catches the bridge-only case, which is the more common failure mode for SBMs that fit on between-block edge density rather than within-block cohesion. The cost: WCC may over-split a sparse-by-design cluster, the kind of tree-like community whose mincut is genuinely 1. The paper reports the gain holds when the input clustering is suspected to over-merge.

The CM page covers the heavier sibling: same cut, plus a re-cluster of each half via the base algorithm. WCC just cuts. The minimum-cut work is delegated to VieCut, whose own page walks the cactus mincut step-by-step on this same fixture.

stage 0.5 · the threshold function

What \(f(n)\) looks like, and why it grows slowly.

The well-connectedness test is one inequality:

\[ \text{mincut}(C) \;>\; f(|C|) \]

In words: the smallest edge cut of cluster \(C\) must strictly exceed the threshold evaluated at the cluster's own size. The binary accepts three families of \(f\):

\[ f(n) \;=\; C \log_x(n) \qquad f(n) \;=\; C\, n^{x} \qquad f(n) \;=\; \text{piecewise bands in } n \]

The default is \(C=1, x=10\), so \(f(n) = \log_{10}(n)\). In words: a 100-node cluster must survive at least one excess edge above the 2-cut floor; a 1000-node cluster, three. Two interesting properties: the threshold uses base-10 logs so a cluster ten times larger raises the bar by exactly 1 (a unit grade); and because logs grow slower than any positive power, the bar stays mild for clusters in the hundreds of thousands.

Why a log of cluster size, not a constant? Park 2024 argues from a tail bound on stochastic block models: a planted community drawn from an Erdős-Rényi-like block has, with high probability, no cut smaller than \(\Theta(\log n)\). Any cluster whose mincut falls below that threshold is, in this asymptotic sense, more likely to be two communities merged than one community badly drawn. A constant threshold (say, mincut ≥ 2) catches the bridge case at small \(n\), but at \(n=10{,}000\) any planted cluster has mincut growing without bound, so a constant bound stops being informative. The log family scales with that informativeness.

Why not a polynomial like \(n^{0.5}\)? The square-root family is harsher: at \(n=100\), \(0.2 \cdot \sqrt{n} = 2\) crosses the log floor (\(\log_{10}(100) = 2\)). For \(n > 100\), the square root pulls ahead; for \(n < 100\), the log family is the harsher of the two. The square root crosses earlier and bites harder on big clusters; small clusters are easier under it. Which family fits the input clustering depends on whether the analyst expects under-cohesive big clusters (sqrt is harsher) or under-cohesive small clusters (log is harsher).

three families · concrete values

f(3) = log10(3) ≈ 0.477, 0.2·√3 ≈ 0.346, piecewise = 1
f(10) = log10(10) = 1.000, 0.2·√10 ≈ 0.632, piecewise = 1
f(100) = log10(100) = 2.000, 0.2·√100 = 2.000, piecewise = 2
f(1000) = log10(1000) = 3.000, 0.2·√1000 ≈ 6.325, piecewise = 3
f(10000) = log10(10000) = 4.000, 0.2·√10000 = 20.000, piecewise = 10

The log family and the sqrt family cross at \(n = 100\) (where both equal 2). The piecewise family hugs the log curve at small \(n\), then switches to a sqrt-with-coefficient-0.1 above \(n=999\). The piecewise schedule deliberately keeps the bar integer-valued, which sidesteps the \(10^{-9}\) tie tolerance the log path needs.

The threshold uses cluster size, not graph size. A 12-node cluster in a 32-node graph evaluates \(f(12)\), not \(f(32)\). Two interesting properties: the verdict on cluster \(C\) does not depend on what the rest of the graph looks like, so the same cluster has the same verdict whether it lives in a 100-node graph or a 100-million-node graph; and the recursion depth is bounded by the cluster's node count (worst case: a chain of 1-cut peels), not the size of the graph, so the walker terminates regardless of how big the input is.

One more property worth noting: the comparison sits strictly above the threshold. A cluster whose mincut exactly equals \(f(n)\) fails, not passes. The binary guards the log-family branch with a \(10^{-9}\) tolerance so floating-point round-off does not accidentally flip the verdict for clusters of integer-log size (where \(f(n)\) lands on an integer that the cut value can match exactly).

termination, in two sentences

Every push-back component has fewer nodes than the popped cluster, so cluster size is a strictly decreasing function of recursion depth. The base case is size 1, which the queue drops on push-back. So the recursion bottoms out, and the worst case is a cluster shredded to a few singletons in at most \(n\) pops.

The threshold name (well-connectedness) lines up with classical connectivity theory. A graph is \(k\)-edge-connected if every cut has at least \(k\) edges, which is the same as saying its mincut is at least \(k\). WCC's test reads as: "the cluster is \(\lceil f(n) \rceil + 1\)-edge-connected, or close enough to count as it under the tolerance band". Cluster B in the fixture is 1-edge-connected (the bridge), and the threshold at \(n=8\) sits below 1, so 1-edge-connectedness counts as well-connected at that size.

stage 1 · pre-pass (CC)

Drop inter-cluster edges, take connected components, seed the queue.

WCC starts the same way as CC: bucket nodes by cluster id, drop edges crossing cluster boundaries, run breadth-first search on each induced subgraph in node-id order. Components of size 1 are dropped from the work queue; the surviving components become the initial queue for the recursive cut loop below.

One subtlety here: the pre-pass treats every cluster the same way regardless of whether it was internally connected in the input. Two cases worth separating. If the input cluster is already one connected piece, the pre-pass produces one queue entry; the cut loop then decides whether to keep it or shred it. If the input cluster is two or more disconnected pieces (same label, different islands), the pre-pass produces one queue entry per island; each island then runs through the cut loop independently. The second case is what the fixture's cluster C shows: nodes 20-25 share one label but live in two disjoint 3-cycles, so the pre-pass splits them into C1 and C2 before any mincut work begins.

Why split first, then check well-connectedness? Because mincut is undefined on a disconnected graph (the cut value is trivially 0). Running the cut loop directly on a disconnected cluster would return cut 0 with an arbitrary bipartition, which is technically correct but wastes a recursion step. The pre-pass is the cheap shortcut: BFS once per cluster, hand the cut loop only connected pieces.

stage 1.5 · per-pop mechanics

Five phases inside every queue pop.

Once the queue is seeded, the cut loop drains it one cluster at a time. Each pop runs the same five-phase routine. The walker in stage 2 lights up each phase as it advances.

phase 1 · pull take the next cluster from the head of the queue. The queue is FIFO. Push-back order matters because clusters from later pops can interleave with the children of earlier pops, not strictly bracket them.
phase 2 · mincut build the induced subgraph on the cluster's nodes, hand it to VieCut's cactus mincut, read back the cut value and the two-sided partition. VieCut returns the most balanced cut among the minimum cuts.
phase 3 · threshold compute \(f(n)\) for this cluster's size. For the log family, this is \(f(n) = c / \ln(x) \cdot \ln(n)\), with \(c / \ln(x)\) precomputed once at startup so per-pop work is one logarithm and one multiplication.
phase 4 · verdict compare the cut to the threshold under the strict-above rule with a \(10^{-9}\) tolerance for the log family. Pass means the cluster is well-connected; fail means it gets shredded.
phase 5 · action on pass, the cluster moves to the survivor list. On fail, the cluster is split at the cut: the in-side connected components are pushed to the queue tail first, then the out-side. Components of size 1 are dropped from the push-back.

Two properties of this routine matter for understanding the partition the algorithm emits. First, the cut loop never re-evaluates a cluster after it lands in the survivor list. A survivor is final the moment its verdict reads pass. Second, the cut loop never sees the inter-cluster edges that the pre-pass dropped; every mincut runs on the induced subgraph of the popped node set, so a cluster's verdict depends only on its own internal edges.

The threshold formula deserves a closer look because the order of operations matters for byte-equal reproducibility. The natural way to write \(C \log_x(n)\) is \(C \cdot \ln(n) / \ln(x)\): one log of \(n\), one log of \(x\), one multiply, one divide. The binary uses a different order: it precomputes \(p = C / \ln(x)\) once at startup, then per pop evaluates \(t = p \cdot \ln(n)\). Two floating-point operations per pop instead of four. Two interesting properties: the per-pop cost is one log call and one multiply, which is the floor for any size-dependent threshold; and the rounding behaviour is fixed at startup, so two runs on the same input return bit-identical thresholds even on platforms where the log function rounds slightly differently from the runtime's default.

The push-back ordering deserves the same care. After a fail, the cut loop walks the in-side first, runs a sub-BFS to find its connected components, pushes every component of size \(>1\) to the queue tail in component-id order. Then it walks the out-side identically. Components of size 1 are dropped. The recursion terminates because every push-back component is strictly smaller than the popped cluster, and the queue cannot grow past the cluster's node count.

what mincut returns vs what WCC does with it

VieCut's cactus mincut returns the minimum cut value plus a bipartition of the cluster into two sides. The bipartition is the consequence of removing those minimum-cut edges. WCC does not pick which edges to remove; it asks VieCut to do that and accepts the bipartition VieCut produces. The two sides may themselves be disconnected once the cut edges are gone, which is why the cut loop runs a sub-BFS on each side to find its connected components before pushing back. The cut edges themselves are not tracked: WCC only cares about the size and the partition.

One more design choice: the cut loop uses a single shared queue, not per-cluster sub-queues. Two interesting consequences. The walker's view of "which clusters remain to process" is the queue itself, in FIFO order, regardless of which input cluster they descended from. And a long-running cluster (one that splits and re-splits) can interleave with siblings, so the cluster popped right after a fail may not be a child of that fail but instead an older sibling waiting in the queue. The walker's queue panel shows this directly.

stage 2 · recursive cut

Mincut, threshold check, repeat.

Each pop pulls a cluster, runs VieCut cactus mincut on its induced subgraph, computes the threshold for the cluster's size, then keeps the cluster (if cut clears threshold) or splits it into the two cut halves and pushes the connected components of each side back onto the queue.

stage 2.5 · worked example

How the recursion plays out on the 32-node fixture.

Cluster A is the only cluster on the fixture that fails the well-connectedness test under \(f(n) = \log_{10}(n)\). The other three clusters pass on first sight. Walking the test cluster by cluster, with mincut values read off the planted topology:

A (n=12, K5 core + 7-node periphery): mincut = 1, threshold ≈ 1.079, fail
B (n=8, two K4 joined by a bridge): mincut = 1, threshold ≈ 0.903, pass
C1 (n=3, a 3-cycle): mincut = 2, threshold ≈ 0.477, pass
C2 (n=3, the other 3-cycle): mincut = 2, threshold ≈ 0.477, pass
D (n=4, two 2-cliques + bridge): mincut = 1, threshold ≈ 0.602, pass

Three observations on this table. B passes despite having a mincut of 1: the threshold at \(n=8\) sits below 1, so a single-bridge cluster of size 8 is still considered well-connected by the log family. D passes for the same reason at a smaller size. C entered the queue as two separate 3-cycles because of stage 1's pre-pass, so the cut loop never sees a single n=6 cluster; each cycle stands on its own.

Cluster A is where the recursion does work. The K5 core has four 1-edge periphery pendants attached (nodes 5, 6, 7, 11) and three 2-edge periphery nodes (nodes 8, 9, 10). VieCut returns a mincut of 1: any of the four single-edge pendants is a 1-edge cut. The most balanced of those 1-cuts is still imbalanced (1 node on one side, 11 on the other), since all four pendant cuts have the same shape. The cluster fails: \(\text{mincut} = 1 \le \log_{10}(12) \approx 1.079\).

The split pushes the size-11 side back to the queue (the singleton side is dropped). At \(n=11\), threshold ≈ 1.041, mincut still 1, fail again. Another pendant peels, leaving \(n=10\). At \(n=10\), the threshold lands at exactly 1.000, and the mincut is still 1. The tolerance guard treats cut equal to threshold as fail, so a third pendant peels. The 9-node residual finally clears: threshold ≈ 0.954, mincut still 1, but 1 strictly exceeds 0.954.

The 9-node residual is the K5 core plus four of the periphery nodes. Empirically (binary-verified, cactus mincut backend, single-threaded), the surviving set is nodes \(\{0, 1, 2, 3, 4, 8, 9, 10, 11\}\): the K5 core plus periphery nodes 8, 9, 10 (each attached by two edges, so they were never the cheapest cut), plus periphery 11 (attached by one edge, but kept because by the time the recursion reaches it, the threshold has already dropped below 1). The three peeled pendants were 5, 6, and 7. Which exact pendant peels first is a tie-break inside VieCut; the order can differ between runs, but the survivor set is stable.

final partition under \(\log_{10}\) on this fixture

A becomes its 9-node residual (the K5 core plus four periphery nodes: 8, 9, 10, 11). B is kept as-is (two K4 joined by the bridge). C splits into two 3-cycles via the pre-pass, both kept. D is kept as-is. The two singleton outliers and the three peeled periphery pendants do not appear in the output: they passed through size-1 short-circuits or were filtered as singletons.

What does the sqrt threshold do on this same fixture? At \(0.2 \sqrt{n}\), A's threshold drops to ≈ 0.693, so the n=12 cut of 1 already passes. B is at 0.566, C₁/C₂ at 0.346, D at 0.4. Every cluster passes on first sight, no peeling. The two criteria agree on B, C, D and disagree on A. On a larger graph the disagreement reverses: above \(n=100\), the sqrt curve climbs past log and becomes the harsher of the two.

Under the piecewise schedule, the thresholds are integer-valued. For \(n < 100\), the cluster only has to clear cut 1; for \(n\) in \([100, 500]\), cut 2; for \(n\) in \((500, 999]\), cut 3; and for \(n > 999\), \(\lceil 0.1 \sqrt{n} \rceil\). Every cluster on the fixture sits in the first band, so the piecewise verdict is "cut \(\ge 1\) means pass". B, C₁, C₂, D pass for the same reason as the sqrt case. A passes too: mincut 1 clears the bar of 1. The piecewise schedule is the most permissive of the three families on small clusters and the harshest on the tail above \(n \approx 10{,}000\), where \(\lceil 0.1 \sqrt{n} \rceil\) leaves \(\log_{10}(n)\) behind.

Picking the doubled coefficient \(2 \log_{10}(n)\) reshuffles the fixture. At \(n=8\), threshold ≈ 1.806, so B (cut 1) now fails. The cut loop splits B at the 15-16 bridge into two K4 of size 4. Each K4 at \(n=4\) has mincut 3 (every edge participates in three triangles, so the smallest cut is the three edges incident to any single node). The threshold at \(n=4\) is \(2 \log_{10}(4) \approx 1.204\), and 3 strictly clears it, so both halves pass. B splits into its two K4; the bridge edge does not come back. This is the only criterion in the picker that splits B in the fixture, which is a useful illustration of how a coefficient bump shifts a single edge's significance.

a clarifying note on the sqrt criterion

The shipped sqrt option in the picker is \(0.2 \sqrt{n}\). Park 2024 also defines a stricter sqrt at \(\sqrt{n}/10\), which is the unit used inside the piecewise schedule's tail (above \(n=999\)). The two coincide except for the coefficient; both have the same crossover with \(\log_{10}\) at \(n=100\) when scaled, but only the 0.2 form is exposed as a top-level option here. The piecewise schedule embeds the \(\sqrt{n}/10\) form as a clamped tail.

stage 2.75 · invariants and corners

What WCC promises and what it does not.

A handful of invariants survive across every queue pop, regardless of input. Reading them in order makes the algorithm a little less mysterious when the walker emits a partition that looks surprising.

cluster size strictly shrinks per recursion every push-back component has fewer nodes than the popped cluster. A push-back of equal size would imply the cut had 0 edges, which only happens on a disconnected cluster (whose pre-pass would have split it first).
survivors are immutable once a cluster passes, it leaves the queue and never returns. WCC is monotone in survivorship; the partition only grows.
survivors carry no input cluster id the output ids run 0, 1, 2, ... in the order survivors are popped from the done-queue. A surviving fragment of the input cluster A does not keep the label "A"; it gets a fresh id. This differs from CM, which preserves lineage through the recursion.
threshold is local two runs on different graphs containing the same cluster (same node set, same internal edges, same induced topology) produce the same verdict for that cluster. The threshold only sees the cluster's size and mincut.
push-back order is in-side first when a cluster fails, the components of the in-partition are pushed before the components of the out-partition. The verdict is identical regardless, but the survivor numbering depends on this order.

A few corner cases that the planted fixture does not stress but the algorithm has to handle:

a sparse community by design

Tree-like clusters (a star, a path, a sparse tree) have genuine mincut 1. Under any non-trivial log or sqrt threshold, they fail and shred down to singletons or pairs. The output can lose every internal node of the cluster. This is the over-splitting failure mode Vu-Le 2026 calls out.

a cluster with weighted edges

VieCut accepts edge weights and computes the minimum weighted cut. The threshold treats the cut value as a real number; clusters with weights ≥ 1 on every edge behave essentially as unweighted. Clusters with sub-unit weights can be shredded much harder than the unweighted intuition suggests.

a cluster of size 2

Either the two nodes share an edge (mincut 1, threshold \(\log_{10}(2) \approx 0.301\), passes) or they do not (the pre-pass already split them as two singletons, both dropped). The size-2 case is the smallest non-trivial cluster the cut loop ever sees.

a cluster that exactly equals the graph

If the input partition has all nodes in one cluster, the pre-pass does no work (no inter-cluster edges to drop). The cut loop runs WCC on the whole graph. Useful as a sanity check: WCC then converges to the maximal well-connected subgraphs of the input graph.

a non-deterministic input partition

If the input partition came from a randomised algorithm (Louvain, Leiden), changing the seed changes the input, which changes which clusters WCC sees. The post-proc itself is deterministic given an input partition, but the joint pipeline is not.

two minimum cuts with the same value

VieCut breaks the tie by picking the most balanced of the tied cuts. The verdict is unaffected (both ties have the same cut value, so both lead to the same pass/fail decision). The push-back composition can differ: one tie peels a single node, another splits the cluster in half.

stage 2.9 · what WCC does not do

The post-proc has a narrow remit.

It is easy to read the recursive-split picture as "WCC re-clusters the graph". It does not. The remit is small enough that listing what falls outside it clarifies the picture.

no re-clustering WCC never re-runs the base clustering algorithm on the split halves. After a split, both halves are pushed back as-is. CM is the sibling that re-runs Leiden (or whichever base) on each half; that is the headline difference between the two.
no merging the post-proc only splits; it never combines two input clusters into one. If the input under-splits a community (one ground-truth community labelled as two clusters), WCC cannot fix it.
no node relabelling across clusters a node assigned to input cluster A is either a survivor of a fragment of A, or unlabelled in the output. It never gets the label of cluster B.
no global mincut WCC computes per-cluster mincut, not graph-wide mincut. The cut found inside cluster A is the smallest cut that splits A; it might be much larger than the smallest cut of the residual graph.
no use of edge attributes other than weight the cut backend reads edge weights and ignores everything else. Edge timestamps, attributes, types: none of them feed the threshold.
no parameter tuning the threshold is a fixed string passed in once. WCC does not pick \(C\) and \(x\) per cluster, and does not adapt the criterion to local density. The single global criterion applies to every cluster.

In the chained pipeline, WCC sits downstream of a base clustering algorithm. The harness tests four bases in rotation: Leiden with modularity, Leiden with CPM at resolution 0.5, Infomap, and the planted-partition SBM. Each base produces an input partition, WCC post-processes it, and the survivor partition feeds downstream analysis. Two interesting properties of this composition: each base has its own failure mode (Leiden's resolution limit, Infomap's two-level coding, the SBM's between-block bias), and WCC catches the bridge-only and disconnected-cluster cases regardless of which base produced them; and the bit-equal verification matrix grids all four bases against the same WCC pipeline, so any base-specific tie-break that flips the WCC output gets surfaced.

why VieCut for the mincut, not Stoer-Wagner

Stoer-Wagner is the textbook minimum-cut algorithm, with one easy-to-state property: it runs in \(O(|V| |E| + |V|^2 \log |V|)\) and returns the global mincut. VieCut's cactus mincut is in expectation linear in graph size, much faster in practice, and returns not just the cut value but the cactus structure that encodes every minimum cut at once. WCC needs the most balanced minimum cut, which the cactus exposes for free; running Stoer-Wagner and then searching among ties would cost much more. The pedagogy walker can fall back to a Stoer-Wagner standin if VieCut is not loaded, but the canonical pipeline runs through VieCut.

stage 4 · what changes at scale

From the 32-node fixture to networks with hundreds of thousands of nodes.

The pedagogy fixture sits at 32 nodes for a reason: every queue pop is one of five or six, and the reader can hold the whole recursion in their head. The same algorithm at \(|V| = 100{,}000\) behaves differently in three ways worth flagging.

First, the work shifts from cluster bookkeeping to mincut. On the 32-node fixture, the cut loop does one cactus mincut per pop, with sub-microsecond cost; the bottleneck is the threshold compare. At a hundred thousand nodes split across a few hundred clusters, each cluster's mincut still runs in near-linear time, but the constants stop being negligible. VieCut's cactus build dominates the wall time, and the threshold compare becomes free in comparison. The chained verification harness uses fixtures up to \(|V| \approx 23{,}000\) to keep the test matrix tractable, with cells running in tens of seconds each.

Second, the recursion depth scales with the structure of the cluster, not the graph as a whole. A cluster with a balanced minimum cut shrinks by roughly half per recursion (log-depth in the cluster's size); a cluster with only 1-cut chains (a long path of pendants) peels one node at a time (linear-depth). Most empirical inputs are somewhere between, and the deepest cluster on a typical graph bottoms out in tens of pops, not thousands. The pre-pass already splits the input into per-cluster work, so the cut loop's total wall time is the sum across clusters rather than a single deep recursion.

Third, the threshold becomes nearly meaningless on huge clusters under the log family. A cluster of \(n = 10^6\) nodes evaluates \(f(n) = 6\), so it has to clear cut 7 to pass. On a typical block-model planted community of that size, the mincut is in the dozens at minimum (every node has expected degree growing with \(n\)). The log family essentially never rejects a huge cluster. The sqrt and piecewise families pull harder at the tail and reject more big clusters.

Vu-Le 2026 empirical findings

Across the SBM variants tested in the paper (graph-tool flat with degree correction, without degree correction, and planted-partition, plus the nested variants and PySBM), WCC consistently improves the recovery of planted communities. The improvement is uniformly larger than CC's. Where the input clustering produces internally disconnected clusters or bridge-only clusters, WCC catches both; CC catches only the first. The exception cases reported are sparse ground-truth communities, where the cluster's mincut is genuinely small and the threshold over-splits a cluster that was already correct. The picker on this page exposes the same tradeoff on the planted fixture.

One last note on the picker: the walker re-runs the kernel on every criterion change, with the same input partition. The number of pops varies with the criterion (harsher criteria split more clusters, which produces more pops). The cut backend is the same VieCut cactus build in every run; the seed is fixed by the URL parameter, so two runs with matching criterion and matching URL produce byte-identical traces. The picker is the only knob that changes behaviour from run to run on this fixture.

stage 5 · verification posture

What "byte-equal versus canonical" means here.

The kernel on this page is a JavaScript port of the binary that ships with the constrained-clustering project. The port is verified against the canonical binary under matched seed and matched input: every cluster popped, every mincut value returned, every threshold computed, every push-back component, all bits identical. The verification matrix sweeps the parameters that drive the kernel's tie-break behaviour: seed (nine values), input partition source (four base algorithms), criterion (three families). Across the full matrix, the survivor sets and the per-pop record fields agree exactly.

Two technical points underpin that match. The threshold is computed in the same order on both sides: a precomputed \(C / \ln(x)\) at startup, then a single multiply with \(\ln(n)\) per pop. Computing it any other way (say, \(C \cdot \ln(n) / \ln(x)\) per pop) introduces a different rounding accumulation. The natural-log primitive itself differs by 1 ulp on a small fraction of inputs between the browser runtime and the system math library; the verification harness ports a faithful natural-log into the canonical binary so the bits line up across the linkage boundary. End readers of the page do not need to know about the port, but it is the reason the walker on this page produces the same partition the binary would.

The mincut backend is delegated to VieCut, which has its own verification matrix. The chained verification here wires VieCut through WCC: a failure at the VieCut layer would surface as a different mincut value or a different bipartition, which would cascade through the WCC verdict and push-back. The matrix grids both layers together, so divergence at either layer is caught.

three claims, three answers

The kernel on this page produces the same partition as the canonical binary, under matched seed and matched input. The canonical binary produces the same partition as the verification tracer (a build of the binary with structured probes that emit per-pop records). The kernel on this page produces the same per-pop trace as the verification tracer. Each of the three claims is checked independently; together they pin down the page as a faithful walker of the binary.
