WCC

well-connected components · Park 2025 / Vu-Le 2026, threshold per Park 2024

A step up from CC. Each cluster has to clear a mincut threshold or it gets cut + recursed. Catches the case where a cluster is connected but only by a thin edge bridge: the kind of cluster that passes CC and still looks suspect to anyone who eyeballs it.

CC only asks whether a cluster is connected. That misses the case where a cluster is connected but only just: two large dense halves linked by a single bridge edge are formally connected, yet anyone eyeballing the graph would call them two communities. The cluster's mincut is 1, and 1 is suspiciously small.

WCC turns "is the cluster connected" into "is the cluster well-connected", with a sliding threshold that scales with cluster size. A cluster passes iff its minimum edge cut strictly exceeds f(n), where n is the cluster's node count and f is one of:

\( f(n) = C \log_x(n) \quad \text{or} \quad f(n) = C\,n^x \quad \text{or piecewise bands of } n \)

The shipped default in constrained-clustering is \( f(n) = \log_{10}(n) \) (Park 2024's choice). Sqrt and \(\log_2\) alternates exist; the binary parses the criterion string straight from the CLI.

If a cluster passes, leave it. If not, find its minimum edge cut, remove those edges, and recurse on each side. The recursion terminates because every cut strictly shrinks the cluster.

mincut the smallest edge set whose removal disconnects the cluster. Computed exactly by VieCut's cactus algorithm in (near-)linear time per cluster (Henzinger, Noe, Schulz, Strash 2018), so even on graphs with thousands of clusters the post-proc stays cheap. Park 2024's mild bound \(f(n) = \log_{10}(n)\) maxes out around 3.3 even for clusters of 2000 nodes.
balanced cut when ties exist (multiple edge sets of the same cut size), the binary picks the most balanced one (find_most_balanced_cut = true in mincut_custom.cpp). This matters: a balanced cut means each recursive half has work to do; an imbalanced cut would peel one node at a time and stall the recursion.
threshold tie-handling the comparison is strict (cut > threshold) with a 1e-9 epsilon guard. Cluster sizes where \(\log_{10}(n)\) equals an integer (n=10, 100, 1000) treat cuts that match the threshold exactly as fail, not pass.
why WCC over CC · Vu-Le 2026 §4

On graph-tool's flat + nested SBMs (every variant tested), WCC's gain over the unprocessed clustering is uniformly larger than CC's. CC catches the disconnected-cluster case; WCC also catches the bridge-only case, which is the more common failure mode for SBMs that fit a partition based on edge density between blocks rather than within. The cost: WCC may over-split a sparse-by-design cluster (a tree-like community whose mincut is genuinely 1). The paper observes WCC's gain holds when the input clustering is suspected to over-merge.

The CM page covers the heavier sibling: same cut, plus a re-cluster of each half via the base algorithm. WCC just cuts.

stage 0 · input

The planted partition.

32 nodes, 52 edges. The criterion below defaults to \(f(n) = \log_{10}(n)\) (Park 2024 default for the binary). Pick a different threshold and the walker re-runs live: the kernel is byte-equal to the canonical binary, so any threshold you set produces the same partition the binary would.

stage 1 · pre-pass (CC)

Drop inter-cluster edges + take connected components.

WCC starts the same way as CC: bucket nodes by cluster id, drop edges crossing cluster boundaries, BFS each induced subgraph in node-id order. Components of size 1 are dropped; surviving components feed the recursive cut loop below as the initial queue.

stage 2 · recursive cut

Mincut, threshold check, repeat.

The walker advances one queue pop at a time. Each pop pulls a cluster, runs VieCut cactus mincut on its induced subgraph, computes the threshold for the cluster's size, then keeps the cluster (if cut clears threshold) or splits it into the two cut halves and pushes the connected components of each side back onto the queue.
