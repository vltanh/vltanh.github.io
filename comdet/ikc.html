IKC

Iterative k-core Clustering

Walk through Wedell, Park, Korobskiy, Warnow + Chacko's IKC algorithm one iteration at a time on the 32-node comdet fixture.

Draft. JS port of community-detection/src/ikc/run_ikc.py against the 32-node fixture; gate verdicts traced per iteration. Shipped IKC's modularity gate is hard-coded to always pass; the page recreates the paper formula for display, with a strict-gate toggle on the outer-loop walker.

Community detection by peeling. Pick a connectivity floor \(k\) (CM-paper default \(k = 10\); the page uses \(k = 4\) on this 32-node fixture so anything surfaces). Compute the \(k\)-core of the residual graph; split it into connected components; gate each component on \(k\)-validity (every node has degree \(\ge k\) inside the kcore) and a modularity check; emit the survivors as clusters; remove their nodes; iterate at \(k - 1\) on the residual until \(K^*\) drops below the floor.

The structure is dual to most CD methods. Louvain and Leiden grow communities by absorbing neighbours; IKC prunes communities by stripping their thinly-attached members. Coverage is loose: anything below \(k\)-validity drops out of the partition entirely (singletons or dropped nodes), so IKC's recall is the lowest in the gallery. Per-cluster core density is the highest: every accepted cluster's induced minimum degree is \(\ge k\) by construction, so it is the sturdiest in the gallery against further peeling. The Wedell paper situates IKC as Stage 1 of a four-stage kmp-clustering pipeline (\(k\)-validity, modularity, and \(p\)-validity for noncore augmentation); this page covers Stage 1 only.

k-core the maximal induced subgraph where every node has degree \(\ge k\). Computed by iterative peel: repeatedly remove every node currently below \(k\); whatever survives is the \(k\)-core.
k-validity a candidate cluster \(C\) is \(k\)-valid iff every node in \(C\) has \(\ge k\) other \(C\)-nodes among its neighbours within the kcore subgraph. Stricter than belonging to the \(k\)-core globally: a node in the global \(k\)-core can still fail \(k\)-validity for its component if its \(k\) qualifying neighbours sit in a different component of the kcore subgraph. The \(k\)-core is necessary, not sufficient.
modularity gate paper formula \[\mathrm{mod}(s) = \ell_s/L - (d_s/2L)^2\] with \(L\) = total edges of the original graph. Shipped IKC short-circuits this to a constant, so the gate is effectively a no-op. The strict-gate toggle on the outer-loop walker switches the constant off and runs the formula.

Core decomposition of this fixture has \(K^* = 4\) (the \(K_5\) in A); the 3-core adds B's two \(K_4\)'s; the 2-core picks up D's 2-cliques + C's 3-cycles + a chunk of A's periphery; the 1-core picks up the dangling pendants. So IKC visits exactly four iterations between \(k = K^*\) and \(k = 1\). For any \(k\)-floor \(\ge 5\) IKC bails on iteration 0; for \(k = 4\) it accepts only the \(K_5\); for \(k = 2\) it accepts four clusters (\(K_5\), B's full bridged 8-node block, both C cycles).

preflight · every node's core number

One integer per node: the densest k-core it survives.

Before any peeling iteration runs, every node has a fixed core number: the largest \(k\) such that the node belongs to the \(k\)-core. The 32-node fixture's distribution lives in the bar below. Each iteration of IKC's outer loop targets one \(k\) bin, in descending order. Shipped IKC computes core numbers via NetworKit's standard core decomposition; the JS port mirrors the Batagelj-Zaversnik bucket-queue algorithm (pop-min, decrement neighbours, repeat). Both then take the slice of nodes with core number \(\ge\) max_k as the kcore subgraph for the iteration.

A node with core number \(k\) belongs to every core down to \(k = 1\), so the \(k\)-core nests inside the \((k - 1)\)-core. IKC exploits the nesting by extracting the \(K^*\)-core first (here just nodes 0..4, the \(K_5\)), removing those nodes, then running core decomposition on the residual graph, where \(K^*\) of the residual drops to 3, and so on. The same nesting gives IKC its determinism: iteration order follows from the input graph and \(k\)-floor.

outer loop · peel, gate, repeat

Top tier off the residual, one tier per iteration.

The IKC outer loop walks the residual graph, not the original. At each iteration: compute \(K^*\) of the current residual; if \(K^* < k_{\mathrm{floor}}\), bail and dump the rest as singletons; otherwise extract the \(K^*\)-core, split it into connected components, and gate each component independently. Surviving components become clusters; their nodes drop out of the residual; the loop iterates with one fewer \(K^*\).

why the residual matters

If IKC ran at every \(k\) on the original graph instead of the residual, every iteration would re-find the same \(K^*\)-core and the loop would not progress. Removing accepted clusters between iterations is what shifts the residual's \(K^*\) downward + lets lower-\(k\) structure surface. On this fixture: iteration 0 at \(k_{\mathrm{floor}} = 2\) yanks \(K_5\) out; iteration 1 sees the residual's max core = 3 (B's bridged 8-block); iteration 2 sees max core = 2 (C's two 3-cycles); iteration 3 finds max core = 1 and bails because that's below \(k_{\mathrm{floor}}\).

result · partition vs planted ground truth

What survives the peeling, side by side with the ground truth.

At default \(k_{\mathrm{floor}} = 2\) on the 32-node fixture, IKC accepts four clusters: the \(K_5\) (5 nodes, k = 4), B's bridged 8-block (8 nodes, k = 3), and both halves of C (3 nodes each, k = 2). 13 nodes drop into the singleton bucket (A's full periphery, D, the outliers). Compare with planted ground-truth: A's periphery + D's modular pair never make it back to their parent cluster; C's two halves are kept separate (planted GT keeps them merged, accepting the disconnect). Singleton clusters never reach the output CSV: the writer strips any cluster of size \(\le 1\) before writing com.csv, so the dropped count above counts nodes filtered at that step plus nodes peeled by failed gates.

on this fixture, by region

At \(k_{\mathrm{floor}} = 2\): A's K_5 surfaces alone in iteration 0, leaving the periphery dangling on edges that no longer count toward k-validity (every periphery node has \(\le 1\) periphery neighbour). B's 8-block survives because the bridge edge \((15, 16)\) still gives every \(K_4\) member a 3rd intra-cluster neighbour. C's two 3-cycles each independently meet \(k = 2\) (every node has 2 neighbours within its triangle). D's two 2-cliques fail (each 2-clique node has only 1 internal neighbour, so they can't reach \(k = 2\)). Outliers 30 + 31 stay singletons by construction.

Slide \(k_{\mathrm{floor}}\) up: at \(k = 3\), B's 8-block survives but C's triangles fall through; at \(k = 4\), only the \(K_5\) makes it; at \(k = 5\), nothing does (the fixture has no 5-core), so iteration 0 bails immediately and com.csv writes empty. Slide it down to \(k = 2\) (the floor of this slider) is the sweet spot: maximally permissive while still rejecting D, the periphery, and the pendants.

Below the slider: at \(k = 1\) the loop runs all the way to a 1-core residual, so dangling pendants pass \(k\)-validity (a leaf has degree 1 \(\ge\) 1 inside its component); at \(k = 0\) the gate is trivially true for every node, so the partition reduces almost to "connected components of the residual". Almost, because the writer still strips singletons before writing com.csv, so any size-1 component (e.g. an isolated outlier) drops out at output time. Connected-component-equivalent in shape; not in size.

shipped vs paper

Shipped IKC has four documented divergences from Wedell 2022 (the dead modularity gate is the headline; m-validity never enforced, p-validity not implemented, and the modularity column placeholder are the others). The technical reference at docs/algorithms/ikc.md covers each.
