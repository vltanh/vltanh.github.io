IKC

Iterative k-core Clustering

Walk through Wedell, Park, Korobskiy, Warnow + Chacko's IKC algorithm one iteration at a time on the 32-node comdet fixture.

Draft. JS port of community-detection/src/ikc/run_ikc.py against the 32-node fixture; gate verdicts traced per iteration. Modularity gate is computed from the paper's formula \(\mathrm{mod}(s) = \ell_s/L - (d_s/2L)^2\) but defaults to canonical's pass-through (POSITIVE_VALUE = 1 in run_ikc.py:280); enable the strict gate via the toggle in stage 3.

Community detection by peeling. Pick a connectivity floor \(k\) (CM-paper default \(k = 10\); the page uses \(k = 4\) on this 32-node fixture so anything surfaces). Compute the \(k\)-core of the residual graph; split it into connected components; gate each component on \(k\)-validity (every node has degree \(\ge k\) inside the kcore) and a modularity check; emit the survivors as clusters; remove their nodes; iterate at \(k - 1\) on the residual until \(K^*\) drops below the floor.

The structure is dual to most CD methods. Louvain and Leiden grow communities by absorbing neighbours; IKC prunes communities by stripping their thinly-attached members. Coverage is loose: anything below \(k\)-validity drops out of the partition entirely (singletons or dropped nodes), so IKC's recall is the lowest in the gallery. Per-cluster core density is the highest: every accepted cluster's induced minimum degree is \(\ge k\) by construction, so it is the sturdiest in the gallery against further peeling. The Wedell paper situates IKC as Stage 1 of a four-stage kmp-clustering pipeline (\(k\)-validity, modularity, and \(p\)-validity for noncore augmentation); this page covers Stage 1 only.

k-core the maximal induced subgraph where every node has degree \(\ge k\). Computed by iterative peel: repeatedly remove every node currently below \(k\); whatever survives is the \(k\)-core.
k-validity a candidate cluster \(C\) is \(k\)-valid iff every node in \(C\) has \(\ge k\) other \(C\)-nodes among its neighbours within the kcore subgraph (run_ikc.py:266-277). Stricter than belonging to the \(k\)-core globally: a node in the global \(k\)-core can still fail \(k\)-validity for its component if its \(k\) qualifying neighbours sit in a different component of the kcore subgraph. The \(k\)-core is necessary, not sufficient.
modularity gate paper formula \(\mathrm{mod}(s) = \ell_s/L - (d_s/2L)^2\) with \(L\) = total edges of the original graph. Canonical runs short-circuit to \(\mathrm{mod} = 1\) (POSITIVE_VALUE in run_ikc.py:280), so the gate is effectively a no-op in shipped IKC. The toggle below switches this off.

stage 1 · core decomposition

Every node has a core number; IKC walks it from the top down.

Before any peeling iteration runs, every node has a fixed core number: the largest \(k\) such that the node belongs to the \(k\)-core. The 32-node fixture's distribution lives in the bar below. Each iteration of IKC's outer loop targets one \(k\) bin, in descending order. Shipped IKC computes core numbers via NetworKit's CoreDecomposition inside kc() at run_ikc.py:224-263; the JS port mirrors the Batagelj-Zaversnik bucket-queue algorithm at ikc.js:54 (pop-min, decrement neighbours, repeat). Both then take the slice of nodes with core number \(\ge\) max_k as the kcore subgraph for the iteration.

A node with core number \(k\) belongs to every core down to \(k = 1\), so the \(k\)-core nests inside the \((k - 1)\)-core. IKC exploits the nesting by extracting the \(K^*\)-core first (here just nodes 0..4, the \(K_5\)), removing those nodes, then running core decomposition on the residual graph, where \(K^*\) of the residual drops to 3, and so on. The same nesting gives IKC its determinism: iteration order follows from the input graph and \(k\)-floor.

stage 2 · outer loop

Compute the residual's max-core, peel it, gate every component.

The IKC outer loop walks the residual graph, not the original (run_ikc.py:83-221). At each iteration: compute \(K^*\) of the current residual; if \(K^* < k_{\mathrm{floor}}\), bail and dump the rest as singletons; otherwise extract the \(K^*\)-core, split it into connected components, and gate each component independently. Surviving components become clusters; their nodes drop out of the residual; the loop iterates with one fewer \(K^*\).

why the residual matters

If IKC ran at every \(k\) on the original graph instead of the residual, every iteration would re-find the same \(K^*\)-core and the loop would not progress. Removing accepted clusters between iterations is what shifts the residual's \(K^*\) downward + lets lower-\(k\) structure surface. On this fixture: iteration 0 at \(k_{\mathrm{floor}} = 2\) yanks \(K_5\) out; iteration 1 sees the residual's max core = 3 (B's bridged 8-block); iteration 2 sees max core = 2 (C's two 3-cycles); iteration 3 finds max core = 1 and bails because that's below \(k_{\mathrm{floor}}\).

invariants at every iteration boundary
  • Accepted clusters are pairwise disjoint, and once a node lands in one it never returns to the residual.
  • Every accepted cluster has size \(\ge 2\) and is \(k\)-valid: every member has \(\ge k\) neighbours inside the cluster.
  • Each iteration's \(K^*\) is monotonically non-increasing: \(K^*(\mathrm{it} + 1) \le K^*(\mathrm{it})\), strictly less whenever any node is peeled.
  • Every accepted cluster carries modularity = 1 in the output column (dead-gate placeholder from run_ikc.py:280), regardless of its actual paper-modularity.

on this fixture, by region

At \(k_{\mathrm{floor}} = 2\): A's K_5 surfaces alone in iteration 0, leaving the periphery dangling on edges that no longer count toward k-validity (every periphery node has \(\le 1\) periphery neighbour). B's 8-block survives because the bridge edge \((15, 16)\) still gives every \(K_4\) member a 3rd intra-cluster neighbour. C's two 3-cycles each independently meet \(k = 2\) (every node has 2 neighbours within its triangle). D's two 2-cliques fail (each 2-clique node has only 1 internal neighbour, so they can't reach \(k = 2\)). Outliers 30 + 31 stay singletons by construction.

Slide \(k_{\mathrm{floor}}\) up: at \(k = 3\), B's 8-block survives but C's triangles fall through; at \(k = 4\), only the \(K_5\) makes it; at \(k = 5\), nothing does (the fixture has no 5-core), so iteration 0 bails immediately and com.csv writes empty. Slide it down to \(k = 2\) (the floor of this slider) is the sweet spot: maximally permissive while still rejecting D, the periphery, and the pendants.

Below the slider: at \(k = 1\) the loop runs all the way to a 1-core residual, so dangling pendants pass \(k\)-validity (a leaf has degree 1 \(\ge\) 1 inside its component); at \(k = 0\) the gate is trivially true for every node, so the partition reduces almost to "connected components of the residual". Almost, because print_clusters at run_ikc.py:45-80 still strips singletons before writing com.csv, so any size-1 component (e.g. an isolated outlier) drops out at output time. Connected-component-equivalent in shape; not in size.

shipped vs paper · four divergences

The shipped run_ikc.py implements a strict subset of Wedell 2022. Four places where the binary diverges from the paper:

  1. Modularity gate is dead. modular() at run_ikc.py:280-282 begins with return POSITIVE_VALUE = 1, so the paper's \(\mathrm{mod}(s) = \ell_s/L - (d_s/2L)^2\) at run_ikc.py:284-296 is never reached. \(k\)-validity is the only real filter. The page computes the paper formula in stage 2 for display only; the "strict mod gate" toggle there enforces \(\mathrm{mod}(s) > 0\) for educational comparison (page-only; canonical never runs it). On this fixture every accepted cluster has positive paper-modularity, so the toggle leaves the partition unchanged; on larger benchmarks it shifts.
  2. m-validity is never enforced. Paper §2.2.2 defines a cluster as m-valid iff its core-induced subgraph is connected and has positive modularity. The connectedness half is satisfied by construction since the gate input is already a weakly-connected component of the kcore subgraph. The modularity half rides on the dead gate above, so the m-valid predicate as a whole reduces to "connected", which is always true.
  3. p-validity is not implemented. Paper §2.2.3 defines a four-stage kmp-clustering pipeline; p-validity is the Stage 3 noncore augmentation that grows each accepted core cluster by attaching outside nodes whose connection to the cluster meets a separate threshold. Shipped src/ikc/ covers Stage 1 only, so every accepted cluster is exactly its core; no peripheral nodes get reattached.
  4. Modularity column in com.csv is a placeholder. Each accepted cluster is written with modularity = 1, the dead-gate constant, not a measurement. Downstream consumers reading the column see 1 for every cluster regardless of structure.
what the page actually runs

The JavaScript kernel under this page is a code-faithful port of community-detection/src/ikc/run_ikc.py. Per-step verification is a 2-leg pipeline: an instrumented Python tracer (NetworKit canonical) and the JS kernel both emit the same per-step JSON trace; a diff harness walks the two streams in lockstep and bit-compares every numeric value. The pipeline closes 63 of 63 cells across the cd_stress_tiers panel (T1 + T2 + T3, n = 800..23k, \(k_{\mathrm{floor}} \in \{2, 3, 5, 8, 10\}\)), with 0 mismatches over 10,481 cumulative records. IKC has no RNG, so the playbook's million-record FP/seed bar collapses; the operative bar is full-panel byte-equal under matching input.

Two canonical-source quirks worth knowing. format_graph at run_ikc.py:303-330 promotes the input to a directed weighted graph with weight = degreeIn(u); the weight is never read by the kernel, and \(k\)-validity sums degreeIn + degreeOut so each undirected edge counts once. Same routine calls removeSelfLoops() at line 326 before the kernel ever sees the graph, so self-loops are stripped at the boundary; the JS port mirrors this in compactSubgraph. Container-iteration order on the kcore subgraph is canonicalized to lex-smallest BFS on both sides, which is what allowed the H-row of the audit grid to close.
