Leiden-CPM

Leiden with the constant Potts model objective

A faithful walk through the move + refine + aggregate loop, one node-visit at a time, on a 32-node fixture engineered to exercise every algorithm in the gallery.

Draft. First-pass walker over a JS port of libleidenalg 0.12.0. Per-stage viz uses the kernel's recorded trace; \(\gamma\) slider replays the run. Verification (ARI vs canonical) per the active plan's Phase 4c §4e matrix is pending.

Leiden is a partition-optimisation algorithm. It searches for a node-to-community assignment that maximises a chosen objective quality function. CPM (constant Potts model) is one such objective: each community pays a per-edge reward and a per-pair size penalty controlled by a single resolution knob \(\gamma\).

The algorithm runs three nested phases in a loop until nothing improves:

local move visit every node in random order; if moving it to a neighbour's community raises \(H\), do it; re-queue the moved node's neighbours.
refinement within each community separately, fan out to singletons and merge them back together one at a time, accepting any non-negative move. Guarantees every output community is internally well-connected.
aggregation collapse each refined sub-community into a super-node; sum edge weights between them; rerun the loop on the smaller graph.

The fixture below is the 32-node graph shared across the comdet gallery. Four planted communities (12 + 8 + 6 + 4 nodes) plus two outliers, ~50 edges, mixing ratio \(\mu \approx 0.12\). Hand-tuned so every CD algorithm has a meaningful disagreement with at least one neighbour's verdict.

stage 1 · singleton init

Every node starts in its own community.

Leiden begins from singletons: 32 nodes, 32 communities, one node each. The initial CPM objective is the sum of intra-community edges minus the size penalty, evaluated on this trivial partition. With \(n_c = 1\) for every community the size penalty vanishes (\(\binom{1}{2} = 0\)), so \(H_0 = -\sum_c e_c = 0\) since no edge is intra-community yet.

singleton partition · \(H_0 = 0\) colour = community id (32 distinct hues)

From here every step adds intra-community edges (raising the \(e_c\) term) and grows community size (raising the size penalty). The optimum is wherever those two pressures balance for the given \(\gamma\).

stage 2 · local moving

Greedy ascent, one node at a time.

The fast local-move pass shuffles every node into a queue, then drains it. For each popped node \(v\), enumerate every neighbour's community plus \(v\)'s own and (when \(v\) is not alone) one fresh empty community. Pick whichever community delivers the largest positive \(\Delta H\); ties are broken by the no-move default (a strict \(\Delta > 10\varepsilon\) threshold). When \(v\) actually moves, every stable neighbour not in \(v\)'s new community gets re-queued.

That re-queuing is what makes the pass converge on small graphs in one or two passes: only nodes whose neighbourhood actually changed get a second look.

stage 3 · refinement

Inside each community, fan back to singletons and merge greedily.

This is the phase Louvain lacked. After local-move, a community can be internally disconnected: a node moved into it for a positive \(\Delta H\) without checking that the existing members reach each other. Refinement fixes this by re-partitioning each community in isolation. Initialise the refined partition at singletons. Sweep nodes once; for each node still alone in its refined community, consider merges only into refined communities that lie within the same post-move community. Accept any move with \(\Delta H \ge 0\) (ties accepted, unlike local-move's strict positive).

The constrained-membership boundary is what makes refinement gentle: it never reaches across the post-move partition, only re-organises within it. The output of refinement is what the next phase actually collapses; the post-move partition is kept around purely to define the "how big a super-node" bookkeeping.

stage 4 · aggregation

Collapse refined sub-communities into super-nodes.

Aggregation builds a smaller graph: one node per refined community, edge weight = sum of original edge weights between the two refined communities (self-loops halved on undirected for canonical igraph storage). Node "size" of a super-node carries the original community's node count. The super-graph keeps the same shape of \(H\) when re-evaluated, so running another local-move pass on it is exactly equivalent to making the original communities try further bulk merges.

If aggregation produces a super-graph whose vertex count strictly drops + the previous level still has more nodes than communities, the loop repeats. Otherwise it stops; what was collapsed last time is the final partition.

Leiden-CPM at \(\gamma = 0.05\) typically finds about 8 communities: A's K_5 + bulk periphery as one, the two B halves (the bridge isn't worth the pair penalty at this \(\gamma\)), the two C cycles separately (they have no edge to merge across), the two D pairs separately, and the outliers grouped with whichever periphery edge they touch. Raise \(\gamma\) and every weak link breaks; lower it and the bridge survives + B becomes one block.
